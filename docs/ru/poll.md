# Poll

Всё, что находится под `client.poll`. Очередь poll — это **`<poll>` из RFC 5730**, и именно так
реестр говорит с вами: всё, что происходит с вашими объектами без вашего запроса в этот момент,
приходит сюда и больше никуда.

Вам ничего не проталкивают и вас никто не вызывает. Уведомление лежит в вашей очереди, пока вы не
запросите его и не подтвердите, а подтверждение уничтожает его в реестре. Значимы обе половины этой
фразы, и из-за второй эта страница почти целиком посвящена порядку, в котором вы делаете эти два
действия.

Каждый метод возвращает [`Response`](responses.md), а код ответа 2000 и выше поднимается как
исключение — см. [Ошибки](errors.md).

## Методы

| Метод | Команда EPP |
|---|---|
| `request()` | `<poll op="req"/>` — 1301 с уведомлением, 1300 при пустой очереди |
| `ack(message_id)` | `<poll op="ack" msgID="…"/>` — **удаляет** уведомление в реестре |
| `drain(handler, limit=0)` | две команды выше в цикле, с подтверждением только после возврата из вашего обработчика |

---

## request

```python
client.poll.request() -> Response
```

Запрашивает уведомление из головы очереди. Очередь есть очередь: одно и то же уведомление приходит на
каждый `request()`, пока его не подтвердили, поэтому клиент, который опрашивает, но не подтверждает,
вечно читает одно сообщение.

```python
notice = client.poll.request()

if notice.code() == 1300:
    return                       # ничего не ждёт

notice.message_id()              # '42' — идентификатор, который вы передаёте в ack()
notice.message_count()           # 3 — сколько сообщений остаётся в очереди
notice.queue_message()           # текст УВЕДОМЛЕНИЯ
notice.queue_message_lang()      # 'uk' | 'ru' | 'en'
notice.queue_date()              # '2026-08-14T10:20:00Z' — когда оно попало в очередь
```

| Код | Значение |
|---|---|
| 1301 | к ответу приложено уведомление; `message_id()` заполнен |
| 1300 | очередь пуста; `message_id()` равен `None`, и подтверждать нечего |

Оба кода из семейства 1xxx, поэтому `is_success()` истинно для обоих и ни один из них не поднимает
исключение. Ветвитесь по `message_id() is not None` — или по `code() == 1300`, — а не по успеху.

```python
notice = client.poll.request()
if notice.message_id() is not None:
    handle(notice)
    client.poll.ack(notice.message_id())
```

### Текст уведомления — это не сообщение результата

**`queue_message()` — это уведомление. `message()` — нет.**

`message()` возвращает `<result><msg>` — служебную строку результата команды, «Command completed
successfully; ack to dequeue», одинаковую в каждом ответе на poll, который реестр когда-либо
отправляет. Чтение уведомления через `message()` даёт вам эту неизменную фразу, отбрасывает
настоящее содержимое, а следующее подтверждение удаляет это содержимое в реестре. Уведомление лежит в
`<msgQ><msg>`, то есть в `queue_message()`.

То же различие относится и к языку. `message_lang()` — это язык служебной строки, который следует за
`lang`, с которым вы вошли; `queue_message_lang()` — это язык самого уведомления, который реестр
выбирает по настройкам уведомлений вашей учётной записи. Совпадать они не обязаны, поэтому читайте
собственный язык уведомления, а не полагайтесь на язык сессии:

```python
text = notice.queue_message()
lang = notice.queue_message_lang() or "en"
show_to_operator(text, lang)
```

`queue_date()` — это собственная строка реестра, как и всякая дата в этой библиотеке: момент, когда
уведомление попало в очередь, а не момент, когда вы его прочитали.

## Что несут уведомления

Уведомление всегда несёт текст. Некоторые виды несут ещё и структурированную нагрузку, и там, где она
есть, действовать нужно по ней: текст написан для человека, нагрузка написана для вашего кода.

| Вид | Структурированная нагрузка | Метод чтения |
|---|---|---|
| Запрос, одобрение, отклонение или отмена трансфера | `<domain:trnData>` / `<contact:trnData>` | `transfer()`, `transfer_status()` |
| Итог действия, которое реестр завершил асинхронно | `<domain:panData>` / `<contact:panData>` | `pending_action_data()` |
| Предупреждение о низком балансе | показатели счёта, когда реестр их прикладывает | `balance()`, `available_credit()` |
| Всё прочее, что реестр хочет вам сообщить | нет | `queue_message()` |

### Запрос трансфера

Самое весомое уведомление из всех, потому что у него есть крайний срок, а у молчания — приговор.

```python
t = notice.transfer()
# {'status': 'pending', 'requested_by': 'ACME', 'requested_at': '2026-08-14T10:00:00Z',
#  'acting_client': 'EXAMPLE', 'act_by': '2026-08-19T10:00:00Z',
#  'expiry_date': '2028-04-01T09:15:00Z'}

if t and t["status"] == "pending" and t["acting_client"] == my_clid:
    client.domain.transfer("approve", notice.object_name())     # или "reject"
```

`act_by` — это крайний срок. **По его истечении реестр подтверждает трансфер**, а не отменяет его,
поэтому теряющий регистратор, который подшил это уведомление вместо того, чтобы ответить на него,
лишится домена. Окно составляет 5 дней. См. [Домены → transfer](domains.md#transfer).

### Итог отложенного действия

Когда команда отвечает **1001**, реестр принял её и завершает асинхронно. Ответ приходит сюда:

```python
pan = notice.pending_action_data()
# {'object': 'example.com.ua', 'success': True,
#  'clTRID': 'PYTHON-SDK-20260814101500-4821-0007',
#  'svTRID': 'SRV-19700101103512-24191-00007',
#  'date': '2026-08-14T10:20:00Z'}
```

Две вещи, в которых нужна точность:

- **Только `success` говорит, сработало ли действие.** Окружающий `1301` означает «вот сообщение», а
  не «ваша операция удалась». Неудавшееся создание приходит совершенно успешным ответом на poll,
  который несёт `success: False`.
- **`svTRID` определяет, на какую операцию это ответ.** Это svTRID *исходной* команды — той, что вы
  получили вместе с 1001, — а не самого poll. Очередь не обязана идти в том порядке, в каком вы
  отправляли, и у вас может быть несколько отложенных операций сразу, поэтому сопоставляйте именно по
  нему, а не считайте, что уведомление относится к вашей последней команде.

```python
if pan is not None:
    booking = bookings_by_svtrid.get(pan["svTRID"])
    if booking is None:
        alert_operator("pending outcome for an operation we do not recognise", pan)
    elif pan["success"]:
        booking.confirm(pan["date"])
    else:
        booking.fail(notice.queue_message())
```

`pending_action_data()` возвращает `None` для уведомления, которое такой нагрузки не несёт, а это
большинство из них, поэтому проверяйте результат до чтения ключей. Сопоставление идёт по локальному
имени, поэтому доменная и контактная нагрузки читаются одинаково, а в `object` лежит имя домена или
идентификатор контакта.

### Предупреждение о низком балансе

Реестр предупреждает до того, как счёт опустеет, потому что иначе вы узнаете об этом из кода 2104
посреди пакета операций. Читайте показатели, а не разбирайте фразу:

```python
if notice.balance() is not None:
    alert_billing(notice.available_credit())
else:
    alert_billing(client.balance().available_credit())
```

Деньги — это точная десятичная строка, а не число с плавающей точкой. См. [Баланс](balance.md).

## ack

```python
client.poll.ack(message_id: str) -> Response
```

Подтверждает одно уведомление, чем **удаляет его в реестре**. Ни отмены подтверждения, ни архива, ни
второй копии не существует: после успешного подтверждения содержимое уведомления живёт только там,
куда его положил ваш код.

```python
r = client.poll.ack(notice.message_id())
r.code()             # 1000
r.message_count()    # сколько осталось, если реестр это сообщил
```

Идентификатор, который ничего не называет — уже подтверждённый или никогда не существовавший, — это
2303.

| Код | Значение |
|---|---|
| 1000 | подтверждено и удалено |
| 2303 | сообщения с таким идентификатором нет: уже подтверждено либо никогда не существовало |

### Подтверждайте после обработки и никогда до неё

В этом и состоит вся операционная дисциплина работы с очередью, и её стоит записать как правило:

> Сохраните уведомление или обработайте его — **и только затем** подтверждайте.

Обратный порядок отказывает молча и необратимо. Цикл, который сначала подтверждает, а потом
обрабатывает, теряет каждое уведомление, обработка которого сорвалась, — запрос трансфера, на который
нужно было ответить за пять дней, итог отложенного создания, под которое у вас всё ещё зарезервированы
деньги, — и не оставляет ни того, с чего можно повторить, ни следа о том, что что-то потеряно. Реестр
его удалил, а это была единственная копия.

```python
# Неверно. Подтверждение фиксирует работу, которая ещё не сделана.
notice = client.poll.request()
client.poll.ack(notice.message_id())
store(notice.queue_message())          # если здесь исключение, уведомления уже нет

# Верно. Ничего не уничтожается, пока работа не сохранена надёжно.
notice = client.poll.request()
if notice.message_id() is not None:
    store(notice.queue_message())      # если здесь исключение, уведомление всё ещё в очереди
    client.poll.ack(notice.message_id())
```

`drain()` существует, чтобы вам не приходилось соблюдать этот порядок вручную.

## drain

```python
client.poll.drain(handler: Callable[[Response], None], limit: int = 0) -> int
```

Читает очередь до конца, передавая каждое уведомление вашему обработчику и подтверждая его **после**
того, как обработчик вернул управление. Возвращает число успешно обработанных уведомлений.

```python
processed = client.poll.drain(lambda notice: store(
    notice.message_id(),
    notice.queue_message(),
    notice.queue_message_lang(),
    notice.queue_date(),
    notice.pending_action_data(),
))
```

| Поведение | Что это значит для вас |
|---|---|
| Подтверждение идёт после возврата из обработчика | Уведомление уничтожается только тогда, когда ваша часть работы сделана. |
| Исключение в обработчике останавливает разбор очереди | Исключение доходит до вас, уведомление **не** подтверждено и остаётся в голове очереди. Устраните причину и разберите очередь снова; ничего не потеряно. |
| Разбор останавливается на первом 1300 | Очередь пуста. Это нормальное завершение. |
| Любой другой ответ без уведомления поднимает исключение | Отказ — закрытая сессия, приостановленная учётная запись — не должен выглядеть как разобранная очередь. Это поднимается даже при `throw_on_failure(False)`, потому что сообщить об успехе, не прочитав ничего, хуже, чем исключение. |
| `limit` ограничивает число обработанных | `0` означает «пока не опустеет». Очередь, которая наполняется быстрее, чем вы её разбираете, иначе оставила бы вызов работать бесконечно. |
| Обработчик `async def` отклоняется | `ValidationException`, до чтения чего-либо. |

Обработчик, который падает всегда, будет видеть одно и то же уведомление при каждом разборе очереди.
Так задумано: альтернатива — выбросить его.

```python
# Разбирайте очередь ограниченными порциями, чтобы один вызов не ушёл в бесконечность.
while client.poll.drain(handle_notice, limit=50) == 50:
    pass
```

### Почему обработчик async отклоняется

`drain()` синхронен. Функция `async def`, вызванная из синхронного кода, немедленно возвращает
корутину и не выполняет ни строки своего тела, поэтому цикл подтвердил бы все уведомления до того,
как хоть одно было обработано, — ровно та потеря, ради предотвращения которой этот метод и
существует, и без единой ошибки в подтверждение. Оберните корутину или ведите очередь сами, через
`request()` и `ack()`:

```python
import asyncio

async def handle(notice):
    await store(notice.queue_message())

# Отклоняется до чтения хотя бы одного кадра:
#   ValidationException: poll.drain() runs synchronously and cannot await an async handler
client.poll.drain(handle)

# Обернём — и порядок снова за drain().
client.poll.drain(lambda notice: asyncio.run(handle(notice)))
```

Либо ведите очередь сами, сохраняя тот же порядок: сначала работа, подтверждение вторым шагом:

```python
async def drain_async(client):
    processed = 0
    while True:
        notice = client.poll.request()
        if notice.message_id() is None:      # 1300: очередь пуста
            break
        await handle(notice)
        client.poll.ack(notice.message_id())
        processed += 1
    return processed
```

### Доставка не реже одного раза

Если сбой происходит на самом подтверждении — соединение обрывается между возвратом из обработчика и
доставкой ack, — уведомление остаётся в очереди, и следующий разбор снова отдаст его вам. Это
безопасное направление отказа, и оно означает, что ваш обработчик обязан спокойно переносить
повторную встречу с уведомлением.

Сделайте его идемпотентным и используйте `message_id()` как ключ отсеивания дубликатов:

```python
def handle_notice(notice):
    message_id = notice.message_id()
    if already_processed(message_id):        # повторная доставка, а не второе событие
        return
    with transaction():
        store(message_id, notice.queue_message(), notice.pending_action_data())
        mark_processed(message_id)
```

Фиксируйте свою часть до подтверждения — и оба направления отказа закрыты: сбой до подтверждения
приводит к повторной доставке, а отсеивание дубликатов её поглощает.

## Законченный поллер

```python
from epptools import Client, Config
from epptools.exceptions import EppException

def handle(notice):
    pan = notice.pending_action_data()
    transfer = notice.transfer()

    if pan is not None:
        reconcile_pending(pan["svTRID"], pan["success"], pan["date"])
    elif transfer is not None and transfer["status"] == "pending":
        queue_for_review(notice.object_name(), transfer["act_by"])
    elif notice.balance() is not None:
        alert_billing(notice.available_credit())
    else:
        store_operator_message(notice.queue_message(), notice.queue_message_lang())

client = Client(Config(host="epp.registry.example", clid="EXAMPLE",
                       password="your-secret", ca_file="/etc/ssl/registry-ca.pem"))
try:
    client.connect()
    client.login()
    print("handled", client.poll.drain(handle), "notices")
    client.logout()
except EppException as exc:
    print("poll run failed:", exc)
finally:
    client.disconnect()
```

Запускайте его по расписанию — обычно раз в несколько минут — и всегда разбирайте очередь до 1300, а
не забирайте по одному уведомлению за запуск. Очередь сокращается только от подтверждений, а запрос
трансфера, прочитанный на четвёртый день, — это запрос трансфера, на ответ по которому у вас остался
один день.

Держите poll на отдельной сессии, если ваш поток операций плотный: одна команда за раз на соединение
— правило, действующее всюду в этой библиотеке, и разбор очереди, делящий соединение с созданием
домена, — это разбор, которому приходится ждать.
