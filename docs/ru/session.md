# Сессия

Всё, что происходит между открытием сокета и его закрытием: как настраивается клиент, как
проверяется TLS, как сессия открывается и закрывается, как меняется пароль, что сервер сообщает о
безопасности сессии и как всё это журналировать, не записав на диск ни одного секрета.

## Форма сессии

```
connect()  →  <greeting>            сервер говорит первым
login()    →  1000                  clID + пароль, сервисы взяты из приветствия
  ... команды, по одной за раз, у каждой свой clTRID ...
logout()   →  1500                  затем сервер закрывает связь
disconnect()                        закрыть сокет
```

Сессия — это TLS-соединение с состоянием. Команды отправляются по одной, и каждый ответ читается до
того, как уйдёт следующая команда; библиотека не конвейеризирует команды, и вам не стоит. Если нужна
пропускная способность, открывайте больше сессий, а не накладывайте команды внутри одной, — но
следите за лимитом одновременных сессий вашей учётной записи: его превышение отклоняется кодом 2502,
и сервер закрывает соединение.

```python
from epptools import Client, Config

client = Client(Config(host="epp.registry.example", clid="EXAMPLE", password="your-secret",
                       ca_file="/path/to/registry-ca.pem"))
client.connect()
client.login()
try:
    print(client.domain.check(["example.com.ua"]).availability())
    client.logout()
finally:
    client.disconnect()
```

## Config, поле за полем
`Config` — неизменяемый dataclass. `host`, `clid` и `password` обязательны и не имеют значений по
умолчанию; у всего остального они есть, и эти значения — правильный ответ для публичной точки
подключения.

```python
from epptools import Config

config = Config(host="epp.registry.example", clid="EXAMPLE", password="your-secret",
                ca_file="/path/to/registry-ca.pem")
```

| Поле | По умолчанию | Что это и что будет, если ошибиться |
|---|---|---|
| `host` | — обязательно | Точка подключения реестра, `epp.registry.example`. Пустая строка вызывает `ConfigException` из `connect()` ещё до того, как откроется сокет. Имя, которое не разрешается, или хост, отказывающий в соединении, вызывает `ConnectionException`. |
| `clid` | — обязательно | Ваш идентификатор регистратора, например `EXAMPLE`. Пустой вызывает `ConfigException` из `login()`. Неверный: вход завершается кодом 2200 (`AuthenticationException`) — так же выглядит и подключение с IP-адреса вне вашего списка разрешённых, поэтому проверьте адрес, прежде чем менять пароль. |
| `password` | — обязательно | Ваш EPP-пароль. Пустой вызывает `ConfigException`. Длина вне диапазона 6–128 символов вызывает `ConfigException` ещё до того, как откроется сокет. Длиннее 16 символов против сервера, который не предлагает RFC 8807, вызывает `ConfigException` с названием расширения, потому что базовый элемент `<pw>` такой пароль не вмещает. Неверный: 2200. |
| `port` | `700` | Порт EPP. Меняйте, только если точка подключения переехала. |
| `lang` | `"en"` | Язык всех сообщений о результате в этой сессии: `en`, `uk`, `ua` или `ru` (`ua` и `uk` — оба украинский). Язык, которого сервер не объявляет, завершает вход кодом 2102. |
| `connect_timeout` | `10.0` | Сколько секунд отводится на TCP-подключение. Превышено: `ConnectionException`, ничего не отправлено. |
| `read_timeout` | `30.0` | Сколько секунд отводится на одно чтение. Значения меньше 1 поднимаются до 1. Превышено: `ConnectionException("Read timed out")`, и соединение закончено — см. [Восстановление соединения](#восстановление-соединения). |
| `verify_peer` | `True` | Проверять цепочку сертификата сервера. `False` отключает проверку полностью; см. предупреждение ниже. |
| `verify_peer_name` | `True` | Проверять, что сертификат соответствует имени хоста, к которому вы подключились. `False` принимает действительный сертификат, выписанный на другое имя. |
| `ca_file` | `None` | Путь к пакету CA, которым подписан сертификат **сервера**. На порту 700 обязателен. Если он задан, этот пакет **заменяет** системное хранилище доверия, а не дополняет его; если не задан, а `verify_peer` включён, используется системное хранилище. Несуществующий путь вызывает `ConnectionException` при `connect()`. |
| `client_cert` | `None` | Ваш клиентский сертификат (PEM) — только там, где точка подключения требует взаимного TLS. Стандартный профиль на порту 700 его не требует. |
| `client_key` | `None` | Закрытый ключ (PEM). Можно опустить, если он вложен в `client_cert`. |
| `client_key_passphrase` | `None` | Парольная фраза для зашифрованного закрытого ключа. Неверная вызывает `ConnectionException` при `connect()`. |
| `obj_uris` | `None` | Переопределяет объектные сервисы, объявляемые в `<login>`. `None` — как и пустой список — означает «ровно то, что предложило приветствие», поэтому сессии никогда не отказывают за просьбу об услуге, которой сервер не обслуживает. URI, который сервер не обслуживает, завершает вход кодом 2307. |
| `ext_uris` | `None` | Переопределяет сервисы расширений. `None` — это то, что было в приветствии. **Пустой список** — это осознанное «не объявлять ни одного расширения», и тогда каждая команда, несущая расширение, получает 2103 — включая DNSSEC, восстановление RGP, цены и запрос баланса. |
| `cltrid_prefix` | `"PYTHON-SDK"` | Первый сегмент каждого сгенерированного клиентского идентификатора транзакции. Держите его коротким: протокол ограничивает идентификатор целиком 64 символами. См. [Команды → Идентификаторы транзакций](commands.md#клиентские-идентификаторы-транзакций). |
| `registry_ext_uri` | `None` | Пространство имён СОБСТВЕННОГО объектного расширения этого реестра. `None` — обычный случай — читает его из приветствия; задавайте вручную только для реестра, чьё расширение названо не по образцу `…/registry-<версия>`, по которому идёт определение. Неверное значение не отвергается: расширение в неизвестном серверу пространстве имён ИГНОРИРУЕТСЯ, поэтому данные молча не доходят. См. [Команды](commands.md#собственные-расширения-вашего-реестра). |
| `registry_balance_uri` | `None` | То же самое для расширения баланса учётной записи. |
| `login_security` | `True` | Участвовать в расширении Login Security (RFC 8807) там, где сервер его предлагает. Именно это и возвращает вам события безопасности от сервера — см. [Безопасность входа](#безопасность-входа-rfc-8807). |

Два поля намеренно исключены из `repr()` этого dataclass: `password` и `client_key_passphrase`.
Dataclass печатает свои поля открытым текстом, так что иначе один `logging.debug("%r", config)`,
один трейсбек, отрисованный вместе с локальными переменными, или один дамп в тесте положили бы
действующий пароль в журнал, который переживёт процесс.

### Config.from_dict

```python
Config.from_dict(values: Dict[str, Any]) -> Config
```

Строит `Config` из обычного отображения, ключи которого — имена полей: конфигурация, прочитанная из
JSON, TOML или из окружения. Ключ, которого среди полей нет, вызывает `ConfigException` с
перечислением нарушителей, а не игнорируется молча: отброшенный `ca_file` — это сессия, которая не
проходит проверку по причине, ничем в конфигурации не объяснимой.

```python
config = Config.from_dict({
    "host": "epp.registry.example",
    "clid": "EXAMPLE",
    "password": os.environ["EPP_PASSWORD"],
    "ca_file": os.environ["EPP_CA"],
})
```

## TLS и сертификат
Транспорт — это EPP поверх TLS (RFC 5734) на порту 700. Клиент отказывается от всего ниже
**TLS 1.2**, поэтому сервер, предлагающий только более старые версии, не проходит рукопожатие, а не
договаривается на понижение.

| Ситуация | Настройка |
|---|---|
| `epp.registry.example:700` — сертификат закрытого CA | задайте `ca_file` на файл `.pem` с CA реестра; **обязательно** |
| Публичный сертификат, которому доверяет браузер | значения по умолчанию (`verify_peer=True`, `verify_peer_name=True`) |
| Правильный сертификат, неправильное имя хоста (разработка) | `verify_peer_name=False` |
| Точка подключения со взаимным TLS | `client_cert` + `client_key` (+ `client_key_passphrase`, если ключ зашифрован) |

Публичная точка подключения предъявляет сертификат, выписанный **собственным закрытым CA реестра**.
В системном хранилище доверия этого CA нет, поэтому `ca_file` должен указывать на пакет, выданный
вам реестром, и без него рукопожатие не проходит. Во всём остальном это строгий EPP по RFC, и
**клиентский сертификат для него не нужен**: вы аутентифицируетесь по clID и паролю поверх TLS, с
IP-адреса из списка разрешённых.

### Когда рукопожатие не проходит

Самый частый сбой при первом запуске — проверка сертификата, и выглядит он так:

```
ConnectionException: TLS handshake with epp.registry.example:700 failed — [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed
```

Почти всегда это значит, что `ca_file` не задан или указывает не на тот пакет. Проверьте пакет вне
Python, прежде чем менять хоть строчку кода:

```bash
openssl s_client -connect epp.registry.example:700 -CAfile /path/to/registry-ca.pem -servername epp.registry.example </dev/null
# "Verify return code: 0 (ok)" означает, что пакет правильный; всё остальное — что нет.
```

За успешным рукопожатием там следует ещё и `<greeting>` сервера прямо в терминале — это
подтверждает, что вы попали на EPP-точку, а не на что-то другое, слушающее этот порт.

**Не хватайтесь за `verify_peer=False`.** Сообщение исчезнет, а вы будете отправлять свой clID, свой
пароль и каждый секрет трансфера тому, кто ответит по этому адресу, без всякой возможности это
заметить. Если рукопожатие не проходит проверку, значит пакет неправильный — попросите у реестра
актуальный. `verify_peer_name=False` — послабление поуже (правильный сертификат, неправильное имя
хоста), и в разработке оно иногда оправданно; `verify_peer=False` не оправдан нигде.

Прочие сбои на этапе рукопожатия вызывают то же `ConnectionException`, с причиной в тексте:
отсутствующий или нечитаемый `ca_file`, `client_cert`, к которому не подходит ключ, неверный
`client_key_passphrase`.

## Открытие и закрытие сессии

| Метод | Возвращает | Что делает |
|---|---|---|
| `Client(config, connection=None, logger=None)` | — | Строит клиент. Ничего не открывает; безопасен на этапе импорта. |
| `Client.connect_and_login(config)` | `Client` | Метод класса: создать, `connect()`, `login()` и вернуть готовый клиент. |
| `connect()` | `Response` | Открывает TLS-сокет и читает незапрошенное `<greeting>`. |
| `greeting` | `Optional[Response]` | Свойство: последнее прочитанное приветствие или `None` до `connect()`. |
| `hello()` | `Response` | Отправляет `<hello>`; сервер отвечает свежим `<greeting>`. |
| `login(new_password=None)` | `Response` | Аутентифицируется (`<login>` из RFC 5730), при желании меняя пароль. |
| `logout()` | `Response` | Завершает сессию; сервер отвечает 1500 и закрывает связь. |
| `disconnect()` | `None` | Закрывает сокет. Безопасно вызывать дважды и безопасно, если подключения не было вовсе. |
| `is_connected()` | `bool` | Открыт ли сокет и годен ли он к работе. |
| `is_logged_in()` | `bool` | Удался ли `login()` на этом соединении. |

**`connect()`** возвращает приветствие как обычный `Response`. Что обслуживает точка подключения,
читается через `service_obj_uris()` и `service_ext_uris()`; именно этот список вход и отражает
обратно. `connect()` на уже открытом соединении читает ещё один кадр, поэтому вызывайте его один раз
за сессию.

**`login()`** объявляет ровно те сервисы, которые предложило приветствие, если только их не
переопределяют `Config.obj_uris` / `ext_uris`, и базовый URI `epp-1.0` никогда не указывается как
объектный сервис. Если вы вызвали `login()`, не вызвав `connect()`, он подключится сам. Всё, кроме
1000, бросает исключение: 2200 — как `AuthenticationException`, остальное — как подходящий класс:
2502 — это лимит сессий, 2501 — сервер закрывает соединение, 2307 — не обслуживаемый URI сервиса,
2002 — второй вход на одном соединении. Назвать всё это ошибкой аутентификации значило бы отправить
вас менять пароль, который тут вообще ни при чём.

**`logout()`** стоит потраченного круга. Если вместо него просто бросить сокет, сессия будет занимать
один из ваших одновременных слотов, пока сервер не закроет её по тайм-ауту, а следующему соединению
могут отказать кодом 2502 из-за слота, которым вы уже не пользуетесь.

**`hello()`** перечитывает приветствие посреди сессии. Это keep-alive для простаивающего соединения
и способ перечитать меню сервисов, не переподключаясь.

`Client` — контекстный менеджер:

```python
with Client(config) as client:
    client.connect()
    client.login()
    ...
    client.logout()          # этот блок за вас его не отправит
```

Блок отключается на выходе, что бы ни случилось, в том числе при исключении. Он не подключается, не
входит и не выходит — держите `logout()` внутри блока, чтобы сессия завершалась корректно, а не по
тайм-ауту.

### Восстановление соединения
`ConnectionException` при чтении или записи означает конец для этого соединения: неудавшаяся
передача оставляет поток байтов на неизвестном смещении, и следующая команда прочитала бы ответ
предыдущей — сдвиг на единицу по тарифицируемым операциям. Любой последующий вызов на нём бросает
исключение, а не продолжает работу на потоке, которому нельзя верить.

Восстановление — это снова `connect()` и `login()`, что заново открывает сокет. Чего делать нельзя,
так это отправлять повторно ту команду, которая не удалась: если это был `create`, `renew` или
`transfer`, её итог по-настоящему неизвестен, а слепой повтор — это то, как домен регистрируется, и
оплачивается, дважды. Сначала спросите у реестра, как обстоит дело; порядок описан в
[Ошибки → Когда итог неизвестен](errors.md#когда-исход-неизвестен).

### Замена транспорта

`Client(config, connection=...)` принимает что угодно, реализующее интерфейс `Transport` —
`open()`, `is_open()`, `write_frame(xml)`, `read_frame()`, `close()`, — и именно так клиента гоняют
по записанному обмену в тестах, без сокета. `Connection` — встроенная реализация поверх TLS, она
используется, когда аргумент опущен.

## Смена пароля

EPP-пароль меняется тем самым входом, который им пользуется (`<newPW>` из RFC 5730), а не отдельной
командой:

```python
client.connect()
response = client.login("a-new-secret")     # аутентифицируется старым, задаёт новый
assert response.code() == 1000
```

Изменение вступает в силу, только если вход удался, и с этого момента старый пароль мёртв.
**Сохраните новый пароль до того, как менять его**, или хотя бы в одной транзакции с этим вызовом:
процесс, который сменил пароль и упал, не успев его записать, закрыл учётной записи вход в любую
будущую сессию, и отменить это может только реестр.

Оба пароля проверяются по длине ещё до того, как откроется сокет. Базовый элемент `<pw>` ограничен
схемой протокола **16 символами**; RFC 8807 поднимает потолок до **128** там, где сервер это
предлагает. Просьба о большем, чем сервер способен унести, вызывает `ConfigException` с названием
расширения — вместо того чтобы отправить кадр, на который сервер ответит голым 2001, не назвав ни
одного поля.

Смена через границу в 16 символов обрабатывается поэлементно, а не покадрово: замена короткого
пароля на длинный переносит в расширение только новый, а старый по-прежнему едет в `<pw>`, где
сервер его и ждёт.

> Прежде чем задавать пароль длиннее 16 символов, проверьте, что ещё аутентифицируется этой учётной
> записью. Пароль, который может ехать только в расширении RFC 8807, невозможно отправить
> программой, работающей с точкой подключения, которая этого расширения не предлагает.

## Безопасность входа (RFC 8807)
Там, где сервер предлагает расширение Login Security, вход несёт небольшой блок с описанием этого
клиента — имя и версию библиотеки, версию Python, операционную систему, — а сервер отвечает всем,
что он хочет видеть исправленным в этой сессии:

```python
for event in client.login().security_events():
    # type:  certificate | cipher | tlsProtocol | password | newPW | stat | custom
    # level: "warning" или "error"
    # text:  предложение, которое показывают оператору
    alert(event["level"], event["type"], event["text"], event.get("exDate"))
```

| `type` | Когда возникает |
|---|---|
| `certificate` | ваш клиентский сертификат близок к истечению — `exDate` содержит точный момент |
| `tlsProtocol` | сессия согласовала устаревшую версию TLS — `name` содержит её |
| `cipher` | сессия согласовала набор шифров, не являющийся AEAD — `name` содержит его |
| `password` / `newPW` | что-то в самих учётных данных, что сервер хочет изменить |
| `stat` | статистика сессии, которую сервер решил сообщить |
| `custom` | специфичное для сервера; `name` его идентифицирует |

У каждой записи всегда есть `text`, а кроме него — те из `type`, `name`, `level`, `exDate`, `value`,
`duration` и `lang`, которые использовало событие. На здоровой сессии список пуст, поэтому любую
запись считайте поводом действовать, а не шумом. Чаще всего это клиентский сертификат, подходящий к
дате истечения; альтернатива тому, чтобы узнать об этом здесь, — узнать утром, когда он перестанет
работать.

Сервер отправляет их только клиенту, который **принял участие** в расширении, потому что объявить
URI — ещё не доказательство умения его прочитать: многие клиенты формируют свой `<svcExtension>`,
просто возвращая приветствие обратно. Поэтому блок уходит даже тогда, когда нести в нём нечего, и
поэтому у клиента, остающегося вне расширения, `security_events()` пуст.

Задайте `login_security=False`, чтобы остаться вне его. Тогда оно используется только там, где без
него никак: для пароля длиннее тех 16 символов, которые вмещает базовый элемент `<pw>`, — такому
паролю больше некуда деться.

## Журналирование
```python
import logging

logging.basicConfig(level=logging.DEBUG)
client = Client(config, logger=logging.getLogger("epp"))
# или позже, а с None — чтобы выключить обратно:
client.set_logger(logging.getLogger("epp"))
```

`set_logger(logger)` возвращает клиент, поэтому вызовы сцепляются. Подойдёт любой объект с методами
`debug`, `info` и `warning`; очевидный выбор — `logging.Logger`.

| Уровень | Что записывается |
|---|---|
| `DEBUG` | приветствие и каждый кадр запроса и ответа целиком |
| `INFO` | одна строка на каждую удавшуюся команду: код ответа, svTRID и clTRID |
| `WARNING` | та же строка для команды, которую реестр отклонил |

**Секреты маскируются до того, как хоть что-нибудь будет записано.** Каждый элемент `<pw>` и
`<newPW>` заменяется в записанном кадре на `***` — при любом префиксе пространства имён и с любыми
атрибутами, какие бы элемент ни нёс, — а это покрывает пароль входа, новый пароль при смене и
секреты трансфера `<domain:pw>` / `<contact:pw>` внутри `authInfo`. Маскирование применяется к
тексту, который передаётся логгеру, поэтому оно действует при любом подключённом вами обработчике.

Всё это — собственные журналы библиотеки. Если вы записываете кадры сами (а во время интеграции это
вполне может понадобиться), вычищайте те же три элемента до того, как текст попадёт в файл или в
обращение в поддержку: `<pw>`, `<newPW>` и `<authInfo>` — действующие учётные данные, а `authInfo` —
это то, что позволяет любому регистратору забрать у вас домен.

Строку INFO стоит оставить включённой в бою. Оба идентификатора транзакции в одной строке, для
каждой команды, включая удавшиеся, — именно с ними вы сравниваете, когда какая-нибудь из
последующих не удастся.
