# Сесія

Усе між відкриттям сокета і його закриттям: як налаштовується клієнт, як перевіряється TLS, як
сесія відкривається і закривається, як змінюється пароль, що сервер повідомляє вам про безпеку
сесії і як усе це журналювати, не записавши на диск жодних облікових даних.

## Форма сесії

```
connect()  →  <greeting>            сервер говорить першим
login()    →  1000                  clID + пароль, сервіси взято з привітання
  ... команди, по одній за раз, кожна зі своїм clTRID ...
logout()   →  1500                  далі сервер закриває з'єднання
disconnect()                        закрити сокет
```

Сесія — це TLS-з'єднання зі станом. Команди надсилаються по одній, і кожна відповідь читається до
того, як піде наступна команда; бібліотека не конвеєризує їх, і вам не варто. Якщо потрібна
пропускна здатність, відкривайте більше сесій, а не накладайте команди в одній, — але зважайте на
обмеження одночасних сесій вашого облікового запису, бо його перевищення відхиляється з 2502, і
сервер закриває з'єднання.

```python
from epptools import Client, Config

client = Client(Config(host="epp.registry.example", clid="EXAMPLE", password="your-secret",
                       ca_file="/path/to/registry-ca.pem"))
client.connect()
client.login()
try:
    print(client.domain.check(["example.com.ua"]).availability())
    client.logout()
finally:
    client.disconnect()
```

## Config, поле за полем

`Config` — це незмінний dataclass. `host`, `clid` і `password` обов'язкові й не мають типового
значення; усе решта має, і ці типові значення — правильна відповідь для публічної точки підключення.

```python
from epptools import Config

config = Config(host="epp.registry.example", clid="EXAMPLE", password="your-secret",
                ca_file="/path/to/registry-ca.pem")
```

| Поле | Типове значення | Що це таке і що буде, якщо воно хибне |
|---|---|---|
| `host` | — обов'язкове | Точка підключення реєстру, `epp.registry.example`. Порожній рядок підіймає `ConfigException` з `connect()` ще до того, як буде відкрито сокет. Ім'я, яке не розв'язується, або хост, що відхиляє з'єднання, підіймає `ConnectionException`. |
| `clid` | — обов'язкове | Ваш ідентифікатор реєстратора, напр. `EXAMPLE`. Порожній підіймає `ConfigException` з `login()`. Хибний: вхід не вдається з 2200 (`AuthenticationException`) — і так само виглядає підключення з IP поза вашим списком дозволених, тож перевірте адресу, перш ніж міняти пароль. |
| `password` | — обов'язкове | Ваш пароль EPP. Порожній підіймає `ConfigException`. Поза межами 6–128 символів підіймає `ConfigException` ще до того, як буде відкрито будь-який сокет. Довший за 16 проти сервера, який не пропонує RFC 8807, підіймає `ConfigException` із назвою розширення, бо базовий елемент `<pw>` його не вміщає. Хибний: 2200. |
| `port` | `700` | Порт EPP. Змінюйте, лише якщо точка підключення переїде. |
| `lang` | `"en"` | Мова всіх повідомлень про результат у цій сесії: `en`, `uk`, `ua` чи `ru` (`ua` і `uk` — обидва українська). Мова, якої сервер не оголошує, завалює вхід із 2102. |
| `connect_timeout` | `10.0` | Скільки секунд відведено на TCP-підключення. Перевищено: `ConnectionException`, нічого не надіслано. |
| `read_timeout` | `30.0` | Скільки секунд відведено на одне читання. Значення менші за 1 підіймаються до 1. Перевищено: `ConnectionException("Read timed out")`, і з'єднання вичерпано — див. [Відновлення з'єднання](#відновлення-зєднання). |
| `verify_peer` | `True` | Перевіряти ланцюжок сертифіката сервера. `False` вимикає перевірку повністю; див. попередження нижче. |
| `verify_peer_name` | `True` | Перевіряти, що сертифікат відповідає імені хоста, до якого ви підключилися. `False` приймає дійсний сертифікат, виданий на інше ім'я. |
| `ca_file` | `None` | Шлях до набору CA, який підписує сертифікат **сервера**. Обов'язковий на порту 700. Якщо задано, цей набір **замінює** системне сховище довіри, а не додається до нього; якщо не задано, а `verify_peer` увімкнено, використовується системне сховище. Неіснуючий шлях підіймає `ConnectionException` у `connect()`. |
| `client_cert` | `None` | Ваш клієнтський сертифікат (PEM), лише там, де точка підключення вимагає взаємного TLS. Стандартний профіль на порту 700 його не вимагає. |
| `client_key` | `None` | Приватний ключ (PEM). Можна пропустити, коли його вкладено в `client_cert`. |
| `client_key_passphrase` | `None` | Парольна фраза до зашифрованого приватного ключа. Хибна підіймає `ConnectionException` у `connect()`. |
| `obj_uris` | `None` | Перевизначає об'єктні сервіси, оголошені в `<login>`. `None` — як і порожній список — означає «рівно те, що запропонувало привітання», і саме тому сесії ніколи не відмовляють за запит сервісу, якого сервер не обслуговує. URI, якого сервер не обслуговує, завалює вхід із 2307. |
| `ext_uris` | `None` | Перевизначає сервіси розширень. `None` означає «ті, що в привітанні». **Порожній список** — це свідоме «не оголошувати жодного розширення», і кожна команда, що несе розширення, тоді отримує 2103 — включно з DNSSEC, відновленням RGP, тарифами та запитом балансу. |
| `cltrid_prefix` | `"PYTHON-SDK"` | Початковий сегмент кожного згенерованого клієнтського ідентифікатора транзакції. Тримайте його коротким: протокол обмежує весь ідентифікатор 64 символами. Див. [Команди → Ідентифікатори транзакцій](commands.md#клієнтські-ідентифікатори-транзакцій). |
| `registry_ext_uri` | `None` | Простір імен ВЛАСНОГО об'єктного розширення цього реєстру. `None` — звичайний випадок — читає його з привітання; задавайте вручну лише для реєстру, чиє розширення назване не за зразком `…/registry-<версія>`, за яким іде визначення. Хибне значення не відхиляється: розширення у просторі імен, невідомому серверу, ІГНОРУЄТЬСЯ, тож дані мовчки не доходять. Див. [Команди](commands.md#власні-розширення-вашого-реєстру). |
| `registry_balance_uri` | `None` | Те саме для розширення балансу облікового запису. |
| `login_security` | `True` | Брати участь у розширенні Login Security (RFC 8807), коли сервер його пропонує. Саме те, що воно лишається увімкненим, і повертає вам події безпеки від сервера — див. [Безпека входу](#безпека-входу-rfc-8807). |

Два поля навмисно виключено з `repr()` цього dataclass: `password` і `client_key_passphrase`.
Dataclass друкує свої поля відкритим текстом, тож один `logging.debug("%r", config)`, один
трейсбек, відрендерений з локальними змінними, або один дамп у тесті інакше поклали б живий пароль
у файл журналу, який переживе процес.

### Config.from_dict

```python
Config.from_dict(values: Dict[str, Any]) -> Config
```

Будує `Config` зі звичайного відображення, ключі якого є іменами полів, — конфігурації, прочитаної
з JSON, TOML чи середовища. Ключ, який не є полем, підіймає `ConfigException` із переліком
порушників, а не ігнорується: мовчки відкинутий `ca_file` — це сесія, що не проходить перевірку з
причини, якої ніщо в конфігурації не пояснює.

```python
config = Config.from_dict({
    "host": "epp.registry.example",
    "clid": "EXAMPLE",
    "password": os.environ["EPP_PASSWORD"],
    "ca_file": os.environ["EPP_CA"],
})
```

## TLS і сертифікат

Транспорт — це EPP поверх TLS (RFC 5734) на порту 700. Клієнт відмовляється від усього нижчого за
**TLS 1.2**, тож сервер, який пропонує лише старіші версії, не проходить рукостискання, а не
узгоджує щось слабше.

| Випадок | Config |
|---|---|
| `epp.registry.example:700` — сертифікат приватного CA | задайте `ca_file` на `.pem` реєстрового CA; **обов'язково** |
| Публічний сертифікат, якому довіряють браузери | типові значення (`verify_peer=True`, `verify_peer_name=True`) |
| Правильний сертифікат, неправильне ім'я хоста (розробка) | `verify_peer_name=False` |
| Точка підключення зі взаємним TLS | `client_cert` + `client_key` (+ `client_key_passphrase`, якщо ключ зашифровано) |

Публічна точка підключення пред'являє сертифікат, виданий **власним приватним CA** реєстру.
Системне сховище довіри цього CA не містить, тож `ca_file` має вказувати на набір, який видав вам
реєстр, і без нього рукостискання не вдається. Поза цим це строгий EPP за RFC, і **клієнтський
сертифікат не потрібен**: ви автентифікуєтеся за clID і паролем поверх TLS, з IP-адреси зі списку
дозволених.

### Коли рукостискання не вдається

Найчастіший збій на першому запуску — це перевірка сертифіката, і виглядає він так:

```
ConnectionException: TLS handshake with epp.registry.example:700 failed — [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed
```

Майже завжди це означає, що `ca_file` не задано або він вказує на не той набір. Перевірте набір поза
Python, перш ніж міняти будь-який код:

```bash
openssl s_client -connect epp.registry.example:700 -CAfile /path/to/registry-ca.pem -servername epp.registry.example </dev/null
# "Verify return code: 0 (ok)" означає, що набір правильний; будь-що інше означає, що ні.
```

За успішним рукостисканням там-таки в терміналі йде `<greeting>` сервера, і це підтверджує, що ви
дісталися саме EPP-точки підключення, а не чогось іншого, що слухає на цьому порту.

**Не хапайтеся за `verify_peer=False`.** Воно прибирає повідомлення і лишає вас надсилати свій
clID, свій пароль і кожен трансферний код тому, хто відповість на цій адресі, без жодної змоги
дізнатися, що так сталося. Якщо рукостискання не проходить перевірку, набір неправильний — попросіть
у реєстру чинний. `verify_peer_name=False` — вужче послаблення (правильний сертифікат, неправильне
ім'я хоста), і зрідка воно розумне під час розробки; `verify_peer=False` не розумне ніде.

Інші збої під час рукостискання підіймають той самий `ConnectionException`, а причина буде в
повідомленні: відсутній або нечитний `ca_file`, `client_cert`, ключ до якого не підходить, хибна
`client_key_passphrase`.

## Відкриття та закриття сесії

| Метод | Повертає | Що робить |
|---|---|---|
| `Client(config, connection=None, logger=None)` | — | Будує клієнта. Нічого не відкриває; безпечно під час імпорту. |
| `Client.connect_and_login(config)` | `Client` | Метод класу: створити, `connect()`, `login()` і віддати готового клієнта. |
| `connect()` | `Response` | Відкриває TLS-сокет і читає незапитане `<greeting>`. |
| `greeting` | `Optional[Response]` | Властивість: останнє прочитане привітання або `None` до `connect()`. |
| `hello()` | `Response` | Надсилає `<hello>`; сервер відповідає свіжим `<greeting>`. |
| `login(new_password=None)` | `Response` | Автентифікує (RFC 5730 `<login>`), за потреби змінюючи пароль. |
| `logout()` | `Response` | Завершує сесію; сервер відповідає 1500 і закриває з'єднання. |
| `disconnect()` | `None` | Закриває сокет. Безпечно викликати двічі й безпечно, якщо підключення не було взагалі. |
| `is_connected()` | `bool` | Чи відкритий сокет і чи придатний до роботи. |
| `is_logged_in()` | `bool` | Чи вдався `login()` на цьому з'єднанні. |

**`connect()`** повертає привітання як звичайний `Response`. Прочитайте, що обслуговує ця точка
підключення, через `service_obj_uris()` і `service_ext_uris()`; саме цей перелік вхід відображає
назад. `connect()` на вже відкритому з'єднанні перечитує кадр, тож викликайте його раз на сесію.

**`login()`** оголошує рівно ті сервіси, які запропонувало привітання, якщо `Config.obj_uris` /
`ext_uris` їх не перевизначають, і базовий URI `epp-1.0` ніколи не перелічується як об'єктний
сервіс. Якщо ви викликаєте `login()`, не викликавши `connect()`, він спершу підключиться. Усе, крім
1000, підіймає виняток: 2200 — як `AuthenticationException`, а решта — як клас, що пасує: 2502 — це
обмеження на кількість сесій, 2501 — сервер закриває з'єднання, 2307 — URI сервісу, який не
обслуговується, 2002 — другий вхід на одному з'єднанні. Назвати їх усі помилкою автентифікації
означало б відправити вас міняти пароль, який ніколи не був причиною.

**`logout()`** вартий свого оберту. Якщо натомість просто кинути сокет, сесія займатиме один із
ваших одночасних слотів, доки сервер не завершить її за тайм-аутом, і наступному підключенню можуть
відмовити з 2502 через слот, яким ви вже не користуєтесь.

**`hello()`** перечитує привітання посеред сесії. Це keep-alive для з'єднання, яке інакше простоює,
і спосіб перечитати меню сервісів без перепідключення.

`Client` є контекстним менеджером:

```python
with Client(config) as client:
    client.connect()
    client.login()
    ...
    client.logout()          # блок не надсилає це за вас
```

Блок роз'єднується на виході за будь-яких обставин, зокрема при винятку. Він не підключається, не
входить і не виходить — тримайте `logout()` усередині блока, щоб сесія завершилася коректно, а не за
тайм-аутом.

### Відновлення з'єднання

`ConnectionException` при читанні чи записі є остаточним для цього з'єднання: невдала передача лишає
потік байтів на невідомому зсуві, і наступна команда прочитала б відповідь на попередню — зсув на
одиницю через операції, за які стягуються гроші. Кожен подальший виклик на ньому підіймає виняток, а
не продовжує роботу з потоком, якому не можна довіряти.

Відновлення — це `connect()` і `login()` наново, що відкриває сокет заново. Чого робити не можна —
це надсилати повторно команду, яка не вдалася: якщо це був `create`, `renew` чи `transfer`, її
результат справді невідомий, і сліпий повтор — це те, як домен реєструють і оплачують двічі. Спершу
запитайте в реєстру, як є насправді; процедура — у розділі
[Помилки → Коли результат невідомий](errors.md#коли-результат-невідомий).

### Заміна транспорту

`Client(config, connection=...)` приймає будь-що, що реалізує інтерфейс `Transport` — `open()`,
`is_open()`, `write_frame(xml)`, `read_frame()`, `close()`, — і саме так у тестах клієнта ганяють
проти записаного обміну без сокета. `Connection` — це вбудована реалізація поверх TLS, вона й
використовується, коли аргумент пропущено.

## Зміна пароля

Пароль EPP змінюється тим самим входом, який його використовує (RFC 5730 `<newPW>`), а не окремою
командою:

```python
client.connect()
response = client.login("a-new-secret")     # автентифікує старим, встановлює новий
assert response.code() == 1000
```

Зміна набуває чинності, лише якщо вхід успішний, і з цієї миті старий пароль мертвий.
**Збережіть новий пароль до того, як його міняти**, або принаймні в тій самій транзакції, що й
виклик: процес, який змінив пароль і впав до того, як його зберегти, замкнув обліковий запис для
всіх майбутніх сесій, і скасувати це може лише реєстр.

Обидва паролі перевіряються за довжиною ще до того, як буде відкрито сокет. Базовий елемент `<pw>`
обмежено **16 символами** самою схемою протоколу; RFC 8807 підіймає стелю до **128** там, де сервер
його пропонує. Запит на більше, ніж сервер може вмістити, підіймає `ConfigException` із назвою
розширення, а не надсилає кадр, на який сервер відповідає голим 2001, що не називає жодного поля.

Зміна через межу в 16 символів обробляється поелементно, а не покадрово: заміна короткого пароля на
довгий переносить у розширення лише новий, а старий і далі їде в `<pw>`, де сервер його й очікує.

> Перш ніж встановлювати пароль, довший за 16 символів, перевірте, що ще автентифікується цим
> обліковим записом. Пароль, який може їхати лише в розширенні RFC 8807, не зможе надіслати
> програмне забезпечення, що спілкується з точкою підключення, яка цього розширення не пропонує.

## Безпека входу (RFC 8807)

Там, де сервер пропонує розширення Login Security, вхід несе невеликий блок, що ідентифікує цього
клієнта — назву й версію бібліотеки, версію Python, операційну систему, — а сервер відповідає всім,
що радить вам виправити в цій сесії:

```python
for event in client.login().security_events():
    # type:  certificate | cipher | tlsProtocol | password | newPW | stat | custom
    # level: "warning" або "error"
    # text:  речення, яке можна показати оператору
    alert(event["level"], event["type"], event["text"], event.get("exDate"))
```

| `type` | Коли виникає |
|---|---|
| `certificate` | ваш клієнтський сертифікат наближається до завершення строку — `exDate` містить точний момент |
| `tlsProtocol` | сесія узгодила застарілу версію TLS — `name` містить її |
| `cipher` | сесія узгодила набір шифрів, який не є AEAD — `name` містить його |
| `password` / `newPW` | щось у самих облікових даних, що сервер радить змінити |
| `stat` | статистика сесії, яку сервер вирішив повідомити |
| `custom` | специфічна для сервера; `name` її ідентифікує |

Кожен запис завжди має `text` і несе ті з полів `type`, `name`, `level`, `exDate`, `value`,
`duration` і `lang`, які використала подія. На здоровій сесії список порожній, тож будь-який запис
вважайте приводом діяти, а не шумом. Найчастіший — клієнтський сертифікат, що наближається до дати
завершення строку; альтернатива дізнатися про це тут — дізнатися того ранку, коли він перестане
працювати.

Сервер надсилає це лише клієнту, який **узяв участь** у розширенні, бо оголошення URI не є доказом
уміння його прочитати — багато клієнтів формують свій `<svcExtension>`, просто повертаючи привітання
назад. Саме тому блок іде навіть тоді, коли в ньому нічого не треба передавати, і саме тому
`security_events()` порожній у клієнта, який лишається поза розширенням.

Задайте `login_security=False`, щоб лишитися поза ним. Тоді воно використовується лише там, де без
нього не обійтися, — для пароля, довшого за 16 символів, які вміщає базовий елемент `<pw>`, бо
такому паролю більше нема куди подітися.

## Журналювання

```python
import logging

logging.basicConfig(level=logging.DEBUG)
client = Client(config, logger=logging.getLogger("epp"))
# або пізніше, а з None — щоб вимкнути знову:
client.set_logger(logging.getLogger("epp"))
```

`set_logger(logger)` повертає клієнта, тож викликається ланцюжком. Підійде будь-який об'єкт із
методами `debug`, `info` і `warning`; `logging.Logger` — очевидний вибір.

| Рівень | Що записується |
|---|---|
| `DEBUG` | привітання, а також кожен кадр запиту й відповіді повністю |
| `INFO` | один рядок на успішну команду: код відповіді, svTRID і clTRID |
| `WARNING` | той самий рядок для команди, у якій реєстр відмовив |

**Секрети приховуються ще до того, як щось буде записано.** Кожен елемент `<pw>` і `<newPW>` у
записаному кадрі замінюється на `***` — за будь-якого префікса простору імен і з якими завгодно
атрибутами елемента, — а це покриває пароль входу, новий пароль під час зміни та трансферні коди
`<domain:pw>` / `<contact:pw>` усередині `authInfo`. Приховування застосовується до тексту, який
передається логеру, тож воно тримається для будь-якого підключеного вами обробника.

Це стосується власних журналів бібліотеки. Якщо ви журналюєте кадри самі — а під час інтеграції вам
цього може захотітися, — вилучайте ті самі три елементи, перш ніж текст потрапить у файл чи у
звернення до підтримки: `<pw>`, `<newPW>` та `<authInfo>` є живими обліковими даними, а `authInfo` —
це те, що дозволяє будь-якому реєстратору забрати у вас домен.

Рядок рівня INFO — той, який варто лишити в бойовому середовищі. Обидва ідентифікатори транзакцій в
одному рядку, для кожної команди, включно з тими, що вдалися, — саме з ними ви порівнюєте, коли
пізніша не вдасться.
