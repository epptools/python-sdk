# Помилки

Кожен збій, який викидає ця бібліотека, успадковує `EppException`, тож один `except` ловить усе:

```python
from epptools.exceptions import EppException

try:
    client.domain.create("example.com.ua", years=1, registrant="C1")
except EppException as exc:
    log.error("EPP failed: %s", exc)
```

Далі — **клас існує там, де відрізняється правильний наступний крок, і більше ніде**. Класу на
кожен код відповіді немає, бо для більшості з них ви не писали б різного коду; клас є там, де
відповідь звучить як «поповніть рахунок», «перепідключіться», «оберіть інше ім'я» або «полагодьте
розгортання», бо це чотири різні програми.

`EppException` успадковує `RuntimeError`, тож голий `except ValueError` його не ловить — з двома
навмисними винятками, зазначеними нижче.

## Ієрархія винятків

```
EppException                     (RuntimeError)
├── ConnectionException          transport: TLS, timeout, framing
├── ConfigException              (also ValueError) this client is set up wrong
├── ValidationException          (also ValueError) this call's arguments are wrong
└── CommandException             the registry refused (a result code >= 2000)
    ├── AuthenticationException  2200 — the login itself failed
    ├── InsufficientFundsError   2104
    ├── AuthorizationError       2201, 2202
    ├── ObjectExistsError        2302
    ├── ObjectDoesNotExistError  2303
    ├── ObjectStatusError        2304, 2305
    ├── PolicyError              2306, 2308
    └── SessionError             2500, 2501, 2502
```

| Перехоплюйте | Виникає, коли | Коди | Що робити далі |
|---|---|---|---|
| `ValidationException` | значення в **цьому виклику** непридатне; нічого не надіслано | — | Виправте аргументи. Наступний виклик з іншими аргументами спрацює. |
| `ConfigException` | **клієнт** налаштовано неправильно: немає хоста, немає облікових даних, пароль, якого цей сервер не може нести | — | Полагодьте розгортання. Кожен виклик зриватиметься так само, доки ви цього не зробите. |
| `ConnectionException` | TLS, тайм-аут, кадрування, розсинхронізований потік, некоректний XML від сервера | — | З'єднання завершено. Виконайте `connect()` і `login()` знову — і прочитайте [Коли результат невідомий](#коли-результат-невідомий), перш ніж щось надсилати повторно. |
| `AuthenticationException` | `login()` відхилено | 2200 | clID або пароль неправильні. Не крутіть цикл: повторні збої призводять до блокування адреси. |
| `InsufficientFundsError` | обліковий запис не може оплатити цю операцію | 2104 | **Зупиніть пакет.** Сповістіть того, хто поповнює рахунок, поповніть, продовжте. Кожна наступна платна команда зірветься так само. |
| `AuthorizationError` | об'єкт існує, але не для вас, або `authInfo` не збігається | 2201, 2202 | Це не привід повторювати. Перевірте, що ви володієте об'єктом і що код трансферу актуальний — він старіє. |
| `ObjectExistsError` | уже зареєстровано | 2302 | Оберіть інше ім'я чи ідентифікатор. Повторення не зробить його вільним. Використовуйте `create_auto()`, щоб узагалі уникнути конфліктів ідентифікаторів. |
| `ObjectDoesNotExistError` | немає такого домену, ідентифікатора чи хоста | 2303 | Застарілий ідентифікатор або одрук. Перечитайте власні записи; не створюйте наосліп. |
| `ObjectStatusError` | заважає статус або асоціація | 2304, 2305 | Приберіть те, що вас блокує — `clientHold`, пов'язаний контакт, підпорядкований хост, — і надішліть ту саму команду знову. |
| `PolicyError` | власні правила реєстру відхиляють значення | 2306, 2308 | Команда сформована правильно і ви можете її надсилати; значення не дозволене. Змініть запит. |
| `SessionError` | сервер завершує сесію | 2500, 2501, 2502 | Перепідключіться і ввійдіть знову. Сама команда може бути цілком доброю — 2502 це обмеження на сесії, а не поганий пароль. |
| `CommandException` | будь-який інший код 2000 або вищий | — | Розгалужуйтеся за `.epp_code`. |

Кожен зі спеціалізованих класів усе одно є `CommandException`, тож `except CommandException`,
поставлений останнім, ловить усе, чого ви не назвали.

```python
from epptools.exceptions import (
    CommandException, InsufficientFundsError, ObjectExistsError, SessionError,
)

try:
    client.domain.create(name, years=1, registrant="C1")
except InsufficientFundsError:
    stop_the_batch()
except ObjectExistsError as exc:
    taken.append(exc.subject() or name)
except SessionError:
    reconnect()
except CommandException as exc:
    log.warning("EPP %d on %s: %s", exc.epp_code, name, exc)
```

`AuthenticationException` — це те, що `login()` викидає на 2200. Вхід, відхилений з будь-якої іншої
причини, викидає той клас, який йому відповідає, — обмеження сесій 2502, зупинку сервера 2501,
службовий URI 2307, якого сервер не пропонує, другий вхід 2002 на одному з'єднанні, — бо називати їх
усі помилкою автентифікації означає відправити вас міняти пароль, який ніколи не був причиною.

## Поганий аргумент — це не погана конфігурація

`ValidationException` та `ConfigException` виглядають схоже і потребують протилежних реакцій, тому
вони й розділені на два класи:

| | `ValidationException` | `ConfigException` |
|---|---|---|
| Що не так | аргументи одного виклику | клієнт, розгортання, облікові дані |
| Чия помилка | зазвичай того запиту, який ви обслуговуєте | зазвичай оператора |
| Хто має про це дізнатися | той, хто викликав, — 400 вашому клієнту API, повідомлення у формі | сповіщення тому, хто адмініструє сервіс |
| Чи спрацює наступний виклик | так, з іншими аргументами | ні. Кожен виклик зриватиметься, доки не зміниться розгортання |

Спільний клас лишає сервіс гадати між ними, а хибний здогад повідомляє клієнтові про власну
помилку конфігурації оператора як про його провину — або ховає повну відмову сервісу за «поганим
запитом» у чужому журналі.

Обидва є також `ValueError`, тож `except ValueError`, який у вас уже є, продовжує їх ловити — так
само, як `json.JSONDecodeError` теж є `ValueError`.

### Що спричиняє ValidationException

Коли виникає щось із цього переліку, нічого ще не надіслано — сокет недоторканий, а клієнт
лишається придатним до роботи:

| Що викидає | Чому |
|---|---|
| невідомий ключ у `chg` чи `sec_dns` | ключ, якого ніхто не читає, — це зміна, що не відбувається за фасадом 1000. Повідомлення називає найближчий розпізнаний ключ |
| сума комісії, що не є простим десятковим числом | `'100,00'`, `'$100'` — див. [Баланс](balance.md#обмеження-того-що-ви-погоджуєтеся-заплатити) |
| понад 20 записів про комісії в одному `check` | обмеження на кадр |
| суміш моделей серверів імен в одній команді | RFC 5731 робить `<domain:ns>` вибором |
| `host.update(new_name=...)` | цей реєстр не має перейменування; повідомлення каже, що робити натомість |
| `contact.create()` без e-mail | RFC 5733 його вимагає |
| `auth_info` і `clear_auth_info` в одному `chg` | схема не може виразити обидва |
| `remove_all_dnssec()` разом із `rem_ds_record()` | так само |
| другий `send()` у білдера | один білдер несе одну команду |
| обробник `async def`, переданий у `poll.drain()` | він підтверджував би кожне сповіщення ще до того, як бодай одне було оброблене |
| порожня роль контакту, порожній дайджест, порожній відкритий ключ, ім'я поля, яке не можна приховати | значення не може потрапити в канал передачі |

Кожне з цього інакше було б непрозорою відмовою від реєстру — часто голим 2001, що не називає
жодного поля, — яка надходить уже після спроби виконати команду, або, ще гірше, 1000 на команду, яка
тихо зробила менше, ніж ви просили.

### Що спричиняє ConfigException

| Що викидає | Чому |
|---|---|
| `Config(host="")` під час `connect()` | немає куди підключатися |
| порожній `clid` чи `password` під час `login()` | повідомлення каже, який з двох порожній, не друкуючи жодного |
| пароль поза межами 6–128 символів | перевіряється до відкриття сокета |
| пароль, довший за 16 символів, проти сервера, який не пропонує RFC 8807 | базовий елемент `<pw>` не може його нести; сервер відповів би голим 2001 |
| `Config.from_dict()` з невідомим ключем | налаштування з одруком — це налаштування, яке не застосовано |

Див. [Сесія → Config](session.md#config-поле-за-полем).

## Що несе CommandException

| Член | Тип | Що це |
|---|---|---|
| `.epp_code` | `int` | Код відповіді, який надіслав реєстр |
| `.response` | `Response` | Уся розібрана відповідь — `sv_trid()`, `ext_values()`, усе |
| `.subject()` | `Optional[str]` | Об'єкт, на який поскаржився реєстр, якщо він його назвав |
| `.reasons()` | `List[str]` | Додатковий текст `<extValue><reason>`, понад однорядкове повідомлення |
| `.is_retryable()` | `bool` | Чи може спрацювати надсилання точно тієї самої команди ще раз |
| `str(exc)` | `str` | `EPP 2302: Object exists ('taken.com.ua')` |

```python
try:
    client.domain.check(["example1.com.ua", "example2.com.ua", "taken.com.ua"])
except CommandException as exc:
    exc.epp_code               # 2302
    exc.subject()              # 'taken.com.ua' — котре з трьох
    exc.reasons()              # ['Already registered']
    exc.response.sv_trid()     # ідентифікатор, за яким підтримка знаходить операцію
```

`subject()` — це та частина, яка робить команду з кількома іменами придатною до дій: «EPP 2302:
Object exists» лишає вас з'ясовувати, котре з трьох, а відповідь лежить у `<extValue>`. Він дорівнює
`None`, коли реєстр нічого не назвав, а це часто, тож тримайте власний запасний варіант —
`exc.subject() or name`.

Зберігайте `exc.response.sv_trid()` разом зі збоєм. Це те значення, яке може знайти служба підтримки
реєстру; ваш clTRID не означає нічого ні для кого, крім вас.

## Повторні спроби

```python
exc.is_retryable()
```

**True рівно для чотирьох кодів** і false для всіх інших:

| Код | Клас | Чому повторна спроба може спрацювати |
|---|---|---|
| 2400 | `CommandException` | команда зірвалася з причини на боці сервера, саме тієї миті |
| 2500 | `SessionError` | сервер закриває з'єднання — повторюйте після перепідключення |
| 2501 | `SessionError` | так само |
| 2502 | `SessionError` | досягнуто обмеження сесій — повторюйте після перепідключення або з меншою кількістю сесій |

Усе інше є false навмисно. Повторення 2302 не зробить ім'я вільним; повторення 2104 його не
оплатить; повторення 2306 не змінить політики реєстру. Цикл, який вважає кожен збій тимчасовим,
перетворює одну відмову на бан за перевищення частоти, а заблокована за довбання адреса — гірша
аварія, ніж той збій, з якого все почалося.

Три з цих чотирьох, що є `SessionError`, придатні до повтору **після** перепідключення. Повторення
їх на з'єднанні, яке вже зірвалося, надсилає дані в сокет, з яким сервер уже закінчив:

```python
for name in names:
    try:
        client.domain.create(name, years=1, registrant="C1")
    except SessionError:
        client.disconnect()
        client.connect()
        client.login()
        retry_later.append(name)          # спершу звірити — див. нижче
    except CommandException as exc:
        if not exc.is_retryable():
            raise
        retry_later.append(name)
```

Робіть паузи між спробами і обмежуйте їх кількість. Дві спроби з інтервалом у кілька секунд — це
відновлення; щільний цикл — це відмова в обслуговуванні, яку ви влаштовуєте власному обліковому
запису.

## Читання кодів замість перехоплення винятків

```python
client.throw_on_failure(False)     # повертає клієнта, тож виклики можна ланцюжити
response = client.domain.check(["example.com.ua"])
if not response.is_success():
    log.warning("EPP %d: %s", response.code(), response.message())
```

`ResultCode` має іменовану константу для кожного коду, тож гілці не доведеться писати число:

```python
from epptools import ResultCode

if response.code() == ResultCode.OBJECT_EXISTS:
    ...
```

Дві речі викидають винятки навіть з вимкненим перемикачем, бо натомість немає корисного `Response`,
який можна було б повернути:

- **`login()`**, на будь-якому коді, крім 1000. Немає сесії, в яку можна було б продовжити.
- **`poll.drain()`**, коли poll-відповідь не є ні сповіщенням, ні порожньою чергою. Прочитати
  відмову як «спорожнено» означало б повідомити про успіх, коли нічого не прочитано.

Вимкнути перемикач означає, що тепер помічати кожен збій — ваша справа. `create`, чийого 2104 ніхто
не перевірив, — це домен, який ваша система вважає зареєстрованим.

## Повний перелік кодів відповіді

`1xxx` — успіх. `2xxx` — відмова, і — окрім випадку з невідомим результатом нижче — нічого не
змінено і нічого не списано.

### Успіх

| Код | `ResultCode` | Значення | Що робити |
|---|---|---|---|
| 1000 | `SUCCESS` | виконано | продовжуйте |
| 1001 | `SUCCESS_PENDING` | прийнято, завершується офлайн | **не надсилайте повторно.** Запишіть svTRID; результат надійде як [poll-сповіщення](poll.md#результат-відкладеної-дії) |
| 1300 | `SUCCESS_NO_MESSAGES` | черга poll порожня | припиніть спорожнювати |
| 1301 | `SUCCESS_ACK_TO_DEQUEUE` | додано poll-сповіщення | обробіть його, а потім підтвердіть |
| 1500 | `SUCCESS_END_SESSION` | вихід прийнято | від'єднуйтеся |

### Протокол і синтаксис

| Код | `ResultCode` | Значення | Що робити |
|---|---|---|---|
| 2000 | `UNKNOWN_COMMAND` | сервер не знає цієї команди | перевірте дієслово; звичайна причина — сирий кадр |
| 2001 | `COMMAND_SYNTAX_ERROR` | кадр не задовольняє схему | повідомлення не називає поля: порівняйте кадр з RFC або з командою, яку будує бібліотека |
| 2002 | `COMMAND_USE_ERROR` | правильна команда, невчасно — другий `login()` на одному з'єднанні | виправте послідовність |
| 2003 | `REQUIRED_PARAMETER_MISSING` | бракує обов'язкового елемента, або команда взагалі не несе жодної зміни | надайте його |
| 2004 | `PARAMETER_VALUE_RANGE_ERROR` | значення поза діапазоном — період або погодження про комісію, що не покриває ціну | див. [Баланс](balance.md#що-означає-відмова-з-кодом-2004) |
| 2005 | `PARAMETER_VALUE_SYNTAX_ERROR` | значення некоректне: погана мітка, погана адреса, кирилиця в поштовому блоці `int` | виправте значення |

### Нереалізоване та білінг

| Код | `ResultCode` | Значення | Що робити |
|---|---|---|---|
| 2100 | `UNIMPLEMENTED_PROTOCOL_VERSION` | `<version>` під час входу має бути 1.0 | недосяжне через власний вхід цієї бібліотеки |
| 2101 | `UNIMPLEMENTED_COMMAND` | сервер не реалізує цієї команди | запитайте реєстр, що він обслуговує |
| 2102 | `UNIMPLEMENTED_OPTION` | параметр, якого сервер не реалізує, як-от непідтримувана `lang` | змініть `Config.lang` |
| 2103 | `UNIMPLEMENTED_EXTENSION` | ви скористалися розширенням, якого ця точка підключення не обслуговує | перевірте привітання: `service_ext_uris()` |
| 2104 | `BILLING_FAILURE` | недостатньо коштів — **`InsufficientFundsError`** | зупиніть пакет, поповніть, продовжте |
| 2105 | `NOT_ELIGIBLE_FOR_RENEWAL` | `cur_exp_date` не збігається, або домен не підлягає продовженню | перечитайте `expiry_date()`; це звіряння, а не привід повторювати |
| 2106 | `NOT_ELIGIBLE_FOR_TRANSFER` | об'єкт не підлягає трансферу | перевірте його статуси і правила зони |

### Безпека

| Код | `ResultCode` | Значення | Що робити |
|---|---|---|---|
| 2200 | `AUTHENTICATION_ERROR` | вхід не вдався — **`AuthenticationException`** | виправте облікові дані; не крутіть цикл |
| 2201 | `AUTHORIZATION_ERROR` | об'єкт не ваш — **`AuthorizationError`** | ви ним не володієте або не можете надсилати цю операцію трансферу |
| 2202 | `INVALID_AUTHORIZATION` | `authInfo` неправильний — **`AuthorizationError`** | отримайте актуальний код; код трансферу старіє через 30 днів після встановлення |

### Життєвий цикл об'єкта

| Код | `ResultCode` | Значення | Що робити |
|---|---|---|---|
| 2300 | `OBJECT_PENDING_TRANSFER` | трансфер уже очікує | зачекайте на нього або `approve`/`reject`/`cancel` |
| 2301 | `OBJECT_NOT_PENDING_TRANSFER` | немає чого схвалювати, відхиляти, скасовувати чи запитувати | трансфер уже вирішено |
| 2302 | `OBJECT_EXISTS` | уже зареєстровано — **`ObjectExistsError`** | оберіть інше ім'я чи ідентифікатор |
| 2303 | `OBJECT_DOES_NOT_EXIST` | такого об'єкта немає — **`ObjectDoesNotExistError`** | застарілий ідентифікатор, одрук або вже підтверджений poll-ідентифікатор |
| 2304 | `OBJECT_STATUS_PROHIBITS_OPERATION` | статус це забороняє — **`ObjectStatusError`** | зніміть статус, потім повторіть |
| 2305 | `OBJECT_ASSOCIATION_PROHIBITS_OPERATION` | асоціація це забороняє — **`ObjectStatusError`** | спершу відкріпіть пов'язаний контакт, хост або домен |
| 2306 | `PARAMETER_VALUE_POLICY_ERROR` | правило реєстру відхиляє значення — **`PolicyError`** | змініть запит |
| 2307 | `UNIMPLEMENTED_OBJECT_SERVICE` | цей об'єктний сервіс або ця зона тут не обслуговуються | перевірте привітання |
| 2308 | `DATA_MANAGEMENT_POLICY_VIOLATION` | правило керування даними це відхиляє — **`PolicyError`** | змініть запит |

### Сервер

| Код | `ResultCode` | Значення | Що робити |
|---|---|---|---|
| 2400 | `COMMAND_FAILED` | команда зірвалася на боці сервера | **придатне до повтору**; зробіть паузу, потім спробуйте ще раз чи двічі |
| 2500 | `COMMAND_FAILED_SERVER_CLOSING` | зірвалося, і з'єднання закривається — **`SessionError`** | перепідключіться, увійдіть, потім повторіть |
| 2501 | `AUTHENTICATION_SERVER_CLOSING` | сервер закриває з'єднання — **`SessionError`** | перепідключіться і ввійдіть |
| 2502 | `SESSION_LIMIT_EXCEEDED_SERVER_CLOSING` | забагато одночасних сесій — **`SessionError`** | закрийте сесії, якими не користуєтеся; завжди виконуйте `logout()` |

## Коли результат невідомий

Тайм-аут читання, обірване з'єднання або `ConnectionException` посеред `create`, `renew`, `transfer`
чи `restore` лишає по-справжньому невідомий результат. Реєстр міг виконати команду і списати з вас
гроші ще до того, як відповідь загубилася. Ця бібліотека не може відрізнити одне від іншого, і ви з
винятку теж не можете: читати немає чого.

> **Не повторюйте команду наосліп.** Сліпа повторна спроба — це те, як домен реєструється і
> оплачується двічі.

Замість цього запитайте реєстр, як є насправді, на новому з'єднанні, і звіряйте з відповіді:

| Команда, що зірвалася | Як з'ясувати, що сталося | Повторюйте, лише якщо |
|---|---|---|
| `domain.create` | `domain.info(name)` | домену не існує або він існує під іншим власником |
| `domain.renew` | `domain.info(name)`, порівняйте `expiry_date()` з очікуваним | дата завершення досі стара |
| `domain.transfer("request", …)` | `domain.transfer("query", name)` | жоден трансфер не очікує |
| `domain.restore` | `domain.info(name)`, прочитайте `rgp_status()` | домен досі в `redemptionPeriod` |
| `contact.create` | `contact.info(id)` — або нічого, для `create_auto()` | ідентифікатора не існує |

```python
from epptools.exceptions import ConnectionException, ObjectDoesNotExistError

try:
    created = client.domain.create(name, years=1, registrant="C1", fee=price)
except ConnectionException:
    # З'єднання завершено; доля команди невідома.
    client.disconnect()
    client.connect()
    client.login()

    try:
        info = client.domain.info(name)
    except ObjectDoesNotExistError:
        created = client.domain.create(name, years=1,          # цього справді не сталося
                                       registrant="C1", fee=price)
    else:
        if info.sponsor() == my_clid:
            book_as_registered(name, info.expiry_date())       # це сталося; не надсилайте повторно
        else:
            alert_operator("%s exists and belongs to %s" % (name, info.sponsor()))
```

Три речі, які показує цей приклад, і кожна з них навмисна:

- **Перевірка виконується на новому з'єднанні.** `ConnectionException` означає, що байтовий потік
  перебуває на невідомому зміщенні; сокет завершено, і кожен наступний виклик на ньому викидає
  виняток.
- **`create_auto()` — єдиний випадок, який звірити неможливо.** Кожен виклик генерує новий
  ідентифікатор, тож друга спроба дає другий контакт, а не конфлікт, — і саме тому ідентифікатор
  з'являється лише у відповіді, яку ви втратили. Звіряйте втрачений `create_auto()` вручну.
- **Збій, результату якого ви не можете визначити, заслуговує на увагу оператора**, а не на
  автоматичну другу спробу. Сповіщайте про нього; не складайте його в чергу повторів.

Те саме міркування стосується **1001**: команду прийнято, і вона завершується офлайн. Це не збій і
не привід надсилати повторно. Запишіть svTRID і чекайте на
[poll-сповіщення](poll.md#результат-відкладеної-дії), яке несе результат.

## Пакет, який гідно обробляє збої

```python
from epptools.exceptions import (
    CommandException, InsufficientFundsError, ObjectExistsError, ValidationException,
)

taken, retry_later, refused = [], [], []

for name in names_to_register:
    try:
        client.domain.create_builder(name).years(1).registrant("C1").send()
    except InsufficientFundsError as exc:
        # Це біда не цього імені, а рахунку. Кожне наступне ім'я зірветься так само.
        alert_billing(str(exc))
        break
    except ObjectExistsError as exc:
        taken.append(exc.subject() or name)
    except ValidationException as exc:
        refused.append((name, str(exc)))        # наш власний ввід; нічого не надіслано
    except CommandException as exc:
        if not exc.is_retryable():
            refused.append((name, "EPP %d: %s" % (exc.epp_code, exc)))
            continue
        retry_later.append(name)
```

Уся суть у формі. Один збій зупиняє запуск, бо продовжувати марно; один є результатом на конкретне
ім'я, який треба записати; один узагалі не дійшов до каналу передачі; і лише справді тимчасові
потрапляють у чергу повторів.

## Як повідомити про проблему

Додайте **svTRID** з відповіді (`exc.response.sv_trid()`) і **clTRID**, який надіслав ваш клієнт.
Разом вони ідентифікують точну транзакцію в журналах реєстру, а саме це робить звернення таким, на
яке можна відповісти без зайвого обміну. Надішліть і кадри, якщо можете, але спершу приберіть з них
`<pw>`, `<newPW>` та `<authInfo>`: це живі облікові дані, і бібліотека маскує їх у власних журналах
з тієї самої причини.

Питання про бібліотеку, про кадр, який відхилив реєстр, або про помилку:
**https://github.com/epptools/python-sdk/issues**.
