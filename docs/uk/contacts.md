# Контакти

Усе під `client.contact`. Об'єкти контактів відповідають **RFC 5733**, і кожен метод тут відповідає
рівно одній команді EPP у каналі передачі.

Контакти йдуть першими в будь-якому потоці реєстрації: домен посилається на ідентифікатори, які вже
мають існувати, тож звичайний порядок такий — створити реєстранта і рольові контакти, а потім
[створити домен](domains.md#create), який на них указує.

Кожен метод повертає [`Response`](responses.md), а код відповіді 2000 або вищий викидається як
виняток — див. [Помилки](errors.md).

## Методи

| Метод | Команда EPP |
|---|---|
| `check` | `<check><contact:check>` |
| `info` | `<info><contact:info>` |
| `create` | `<create><contact:create>` |
| `create_auto` | те саме, із зарезервованим ідентифікатором, що змушує реєстр згенерувати ідентифікатор |
| `update` | `<update><contact:update>` |
| `delete` | `<delete><contact:delete>` |
| `transfer` | `<transfer op="…"><contact:transfer>` |

`create_builder(id, email)` та `update_builder(id)` збирають ті самі команди крок за кроком; див.
[Білдери](builders.md).

## check

```python
client.contact.check(ids: List[str]) -> Response
```

Питає, чи вільні ідентифікатори контактів. По одному `<contact:id>` на ідентифікатор,
**щонайбільше 10 на команду** — одинадцятий відхиляється з 2001.

```python
r = client.contact.check(["C1", "EXAMPLE-C2"])

r.availability()                    # {'C1': False, 'EXAMPLE-C2': True}
r.is_available("EXAMPLE-C2")       # True
r.unavailable_reason("C1") # 'in use', або None
```

`is_available()` повертає `None`, коли відповідь нічого не сказала про цей ідентифікатор, — це не те
саме, що «зайнятий», і це варто розрізняти, перш ніж будувати ідентифікатор навколо відповіді.

Перевірка варта окремого обміну кадрами лише тоді, коли ви самі формуєте ідентифікатори. Якщо ні —
[`create_auto()`](#create_auto) знімає це питання цілком.

| Код | Значення |
|---|---|
| 1000 | відповідь отримано; читайте `availability()` |
| 2001 | понад 10 ідентифікаторів в одній команді |

## info

```python
client.contact.info(contact_id: str, auth_info: Optional[str] = None) -> Response
```

Читає контакт. Як власник ви бачите повний запис; як не-власник — публічну підмножину або повний
запис, якщо передасте `auth_info` контакту. *Неправильний* код це 2202; відсутність коду помилкою
не є.

```python
c = client.contact.info("C1")

c.object_name()     # 'C1' — ІДЕНТИФІКАТОР, а не ім'я людини
c.roid()            # власний ідентифікатор об'єкта в реєстрі
c.email()           # 'contact@example.com'
c.voice()           # '+380.441234567'
c.fax()             # або None
c.statuses()        # ['linked'], щойно на нього посилається домен
c.sponsor()         # clID
c.created_by()      # crID          c.created_date()   # crDate
c.updated_by()      # upID, або None c.updated_date()   # upDate, або None
c.auth_info()       # секрет для трансферу — ніколи не пишіть його в журнал
c.disclose()        # {'flag': False, 'elements': ['email', 'voice']} або None

postal = c.postal_info()
postal["int"]["name"]     # 'Ivan Petrenko'          — форма ASCII
postal["int"]["street"]   # ['vul. Khreshchatyk 1']  — список, до 3 рядків
postal["loc"]["city"]     # 'Київ'                   — форма локальним письмом, коли вона є
```

`object_name()` — це ідентифікатор. Ця різниця має значення: пошук елемента `<name>` по всьому
документу у відповіді контакту першим знаходить ім'я *людини*, а подача його назад як
ідентифікатора дає 2303 із заплутаним повідомленням.

| Код | Значення |
|---|---|
| 1000 | відповідь отримано |
| 2202 | ви не власник, а наданий `auth_info` неправильний |
| 2303 | такого контакту немає |

## create

```python
client.contact.create(contact_id: str, *,
                      name: Optional[str] = None,
                      org: Optional[str] = None,
                      street: Optional[List[str]] = None,
                      city: Optional[str] = None,
                      sp: Optional[str] = None,
                      pc: Optional[str] = None,
                      cc: Optional[str] = None,
                      type: str = "int",
                      postal_infos: Optional[List[Dict[str, Any]]] = None,
                      voice: Optional[str] = None,
                      fax: Optional[str] = None,
                      email: Optional[str] = None,
                      auth_info: Optional[str] = None,
                      disclose: Optional[Dict[str, Any]] = None) -> Response
```

Створює контакт. Не платна.

Форма з однією адресою приймає поля адреси безпосередньо — це короткий спосіб записати
найпоширеніший випадок:

```python
r = client.contact.create(
    "C1",
    name="Ivan Petrenko",
    org="Pryklad LLC",
    street=["vul. Khreshchatyk 1"],
    city="Kyiv",
    pc="01001",
    cc="UA",
    voice="+380.441234567",
    email="contact@example.com",
    auth_info="C0ntact-Pw!",
)

r.object_name()    # 'C1'
r.created_date()   # crDate
```

| Параметр | Іде в канал передачі як |
|---|---|
| `name`, `org`, `street`, `city`, `sp`, `pc`, `cc`, `type` | один блок `<contact:postalInfo type="…">` |
| `postal_infos` | кілька таких блоків — див. нижче |
| `voice`, `fax` | `<contact:voice>` / `<contact:fax>`, у формі EPP `+CC.NNNNNNNNN` |
| `email` | `<contact:email>` — **обов'язковий** |
| `auth_info` | `<contact:authInfo><contact:pw>` |
| `disclose` | `<contact:disclose flag="0\|1">` (приватність за RFC 5733) |

`email` перевіряється ще до того, як щось буде надіслано: порожній або відсутній викидає
`ValidationException`, бо RFC 5733 його вимагає, і реєстр усе одно відхилив би кадр повідомленням,
яке читається довше за це.

`<contact:authInfo>` вирушає завжди. Передайте код — і він стане секретом контакту для трансферу;
пропустіть його — і буде надіслано порожній `<contact:pw/>`.

Реєстр вимагає, щоб ідентифікатор мав 3–16 символів з латинських літер, цифр і `-`; будь-що інше
це 2005.

### Обидві поштові форми

Контакт несе один або два блоки `<contact:postalInfo>`, і те, які з них ви надсилаєте, є справжнім
рішенням, а не формальністю:

| `type` | Вміст | Примітки |
|---|---|---|
| `"int"` | **лише ASCII / латиниця** | кирилиця тут відхиляється з 2005. Це та форма, яку реєстр може показати будь-якій стороні, тому потрібна принаймні одна ASCII-форма |
| `"loc"` | локальне письмо — кирилиця для українського реєстранта | необов'язкова і додаткова |

Надсилайте обидві, якщо маєте обидві. Нічого не відкидається, і `contact.info()` повертає все, що ви
надіслали. Для цього використовуйте `postal_infos`:

```python
client.contact.create(
    "C1",
    postal_infos=[
        {"type": "int", "name": "Ivan Petrenko", "org": "Pryklad LLC",
         "street": ["vul. Khreshchatyk 1"], "city": "Kyiv", "pc": "01001", "cc": "UA"},
        {"type": "loc", "name": "Іван Петренко", "org": "ТОВ «Приклад»",
         "street": ["вул. Хрещатик 1"], "city": "Київ", "pc": "01001", "cc": "UA"},
    ],
    voice="+380.441234567",
    email="contact@example.com",
)
```

**`postal_infos` замінює аргументи з однією адресою.** Коли ви його передаєте, `name`, `city`, `cc`
та решта не читаються взагалі — змішування двох форм в одному виклику надсилає лише блоки зі списку.

Кожен блок приймає до 3 рядків `street`, а `city` і `cc` вимагає схема.

### Блок disclose

RFC 5733 дозволяє контакту вказати, які з його елементів можна публікувати. Блок — це прапорець плюс
список елементів, до яких прапорець застосовується; усе, чого немає в списку, отримує протилежне
поводження, тож список нічого не означає без прапорця.

```python
# Приховати e-mail і телефон; усе інше — за політикою реєстру.
disclose={"flag": False, "email": True, "voice": True}

# Приховати адресу й організацію в ОБОХ поштових формах.
disclose={"flag": False, "addr": ["int", "loc"], "org": ["int", "loc"]}

# Погодитися на публікацію імені в обох формах.
disclose={"flag": True, "name": ["int", "loc"]}
```

| Ключ | Значення | У каналі передачі |
|---|---|---|
| `flag` | істиннісне значення | `flag="1"` (публікувати) або `flag="0"` (приховати) |
| `name`, `org`, `addr` | список поштових типів: `["int"]`, `["loc"]` або обидва | по одному елементу на тип |
| `voice`, `fax`, `email` | істиннісне значення | голий елемент, коли істинне |

`name`, `org` та `addr` існують по одному разу на кожну поштову форму, тож вибір робиться **на
кожну форму окремо**. Вказавши лише `["int"]`, ви приховуєте ASCII-адресу, а форма локальним письмом
лишається публічною — налаштування приватності, яке читається як застосоване, але таким не є.

Кожен прапорець тлумачиться як *значення*, а не за істинністю в Python: рядки `"0"`, `"false"` та
`""` тут усі означають хибність. Вони потрапляють до інтегратора з HTML-форм і збереженого JSON, і
всі три є істинними рядками в Python, тож `disclose={"flag": "0"}` означає ПРИХОВАТИ — саме так, як
було написано.

Прочитайте це назад через `disclose()`, де поштові елементи уточнено формою:

```python
client.contact.info("C1").disclose()
# {'flag': False, 'elements': ['addr:int', 'addr:loc', 'email']}
```

| Код | Значення |
|---|---|
| 1000 | створено |
| 2003 | немає поштового блоку або немає e-mail |
| 2005 | некоректне значення: кирилиця в блоці `int`, поганий e-mail, ідентифікатор поза межами 3–16 символів |
| 2302 | такий ідентифікатор уже існує |
| 2306 | правило реєстру відхиляє значення (слабкий `auth_info`) |

## create_auto

```python
client.contact.create_auto(**options: Any) -> Response
Contact.AUTO_ID = "autonic"
```

Створює контакт і дозволяє **реєстру обрати ідентифікатор**. Приймає ті самі іменовані параметри, що
й `create()`; єдина відмінність у тому, що замість вашого надсилається зарезервований ідентифікатор
`autonic`.

```python
handle = client.contact.create_auto(
    name="Ivan Petrenko", city="Kyiv", cc="UA", email="contact@example.com",
).object_name()          # 'c-9f4b2ad10e'

# Використовуйте його всюди, де потрібен ідентифікатор.
client.domain.create("example.com.ua", years=1, registrant=handle)
```

Згенерований ідентифікатор з'являється **у тій відповіді й більше ніде**. Зберігайте його одразу, як
прочитали; немає команди, яка питає «як ти назвав контакт, що я створив хвилину тому».

Це відповідь на дві задачі одразу. Якщо у вас немає схеми найменування, вам не доведеться її
вигадувати. А якщо вона є, вам більше не потрібно ходити по колу навколо 2302, коли хтось забрав
ідентифікатор першим: `autonic` — це запит, а не ім'я, він ніколи не зберігається як ідентифікатор,
і **кожен виклик генерує новий** — тож повторення того самого запиту дає другий контакт, а не
конфлікт. Згенеровані ідентифікатори складаються з малих латинських літер, цифр і `-`, у межах
3–16 символів, які дозволяє протокол.

Зарезервоване значення доступне як `Contact.AUTO_ID`, якщо ви волієте передати його в `create()`
самотужки або в [білдер створення контакту](builders.md), який приймає ідентифікатор аргументом:

```python
from epptools import Contact

client.contact.create(Contact.AUTO_ID, name="Ivan Petrenko", city="Kyiv",
                      cc="UA", email="contact@example.com")
```

Коди відповіді — ті самі, що й у `create`, мінус 2302, у чому й полягає сенс.

## update

```python
client.contact.update(contact_id: str, *,
                      add_statuses: Optional[List[str]] = None,
                      rem_statuses: Optional[List[str]] = None,
                      chg: Optional[Dict[str, Any]] = None) -> Response
```

Змінює контакт. Статуси йдуть у власних аргументах; кожна зміна поля йде в `chg`.

```python
client.contact.update(
    "C1",
    chg={"email": "new-contact@example.com",
         "postal_info": {"name": "Ivan Petrenko", "city": "Lviv", "cc": "UA", "org": ""}},
    add_statuses=["clientUpdateProhibited"],
)
```

`chg` приймає рівно ці ключі, як у написанні snake_case, так і в camelCase з RFC:

| Ключ | Дія |
|---|---|
| `postal_info` / `postalInfo` | один поштовий блок |
| `postal_infos` / `postalInfos` | кілька поштових блоків |
| `voice` | замінити номер телефону; `""` очищає його |
| `fax` | замінити номер факсу; `""` очищає його |
| `email` | замінити e-mail; він обов'язковий, тож очистити його не можна |
| `auth_info` / `authInfo` | замінити секрет для трансферу |
| `disclose` | замінити налаштування розкриття — та сама форма, що й у create |

Будь-який інший ключ викидає `ValidationException`, з підказкою, коли він схожий на одрук. Ключ,
якого ніхто не читає, — це зміна, яка не відбувається за фасадом 1000, і ніщо у відповіді про це не
скаже.

*Прибрати* секрет контакту для трансферу неможливо. RFC 5731 дає домену форму з обнуленням, а
RFC 5733 не визначає для контакту жодного відповідника, тож код контакту можна замінити, але не
очистити. Порожній пароль замінником не є: порожнє значення — це все одно значення, яке той, хто
його має, може пред'явити.

### Правило часткового оновлення: вирішує присутність

Усередині поштового блоку **вирішує присутність, а порожній рядок очищає**:

| Ви пишете | Що відбувається |
|---|---|
| ключа немає | поле не надсилається, і реєстр зберігає те, що має |
| ключ має значення | поле встановлюється в це значення |
| ключ містить `""` | поле надсилається порожнім, що **очищає** його |

Це єдиний спосіб прибрати `org`, `sp` чи `pc`. І це також єдина поштова форма, якої торкаються:
зміна блоку `int` лишає блок `loc` точно таким, як був, і навпаки.

```python
# Прибрати організацію, більше нічого в адресі не змінювати.
client.contact.update("C1",
                      chg={"postal_info": {"type": "int", "org": "",
                                           "city": "Kyiv", "cc": "UA"}})
```

**Вказуйте `city` та `cc` щоразу, коли взагалі торкаєтеся адреси.** Елемент `<contact:addr>` — це
послідовність, у якій місто й країну вимагає схема, тож він надсилається цілком або не надсилається
зовсім, — а коли надсилається, місто й країна йдуть разом з ним. Пропустивши їх у виклику, що змінює
рядок вулиці, ви надсилаєте їх **порожніми**, а порожнє значення — це навмисне очищення. Команда
відповідає 1000, і контакт втрачає своє місто й країну.

Рядки вулиці поводяться інакше і на вашу користь: блок адреси, надісланий без жодного `street`,
лишає наявні рядки недоторканими.

Якщо ви змінюєте лише ім'я, організацію чи телефон, не згадуйте `street`, `city`, `sp`, `pc` чи `cc`
взагалі — тоді жодного блоку адреси не надсилається і ніщо в ньому не може постраждати:

```python
# Адреси не торкаємося, бо ніщо до неї не звернулося.
client.contact.update("C1", chg={"postal_info": {"name": "Ivan Petrenko"}})
```

### Статуси

`add_statuses` та `rem_statuses` будують по одному блоку, що містить кожен названий вами статус.
Клієнтські, які можна встановлювати, — це `clientDeleteProhibited`, `clientUpdateProhibited` та
`clientTransferProhibited`; відповідники `server*` належать реєстру, і команда, що намагається
встановити такий, відхиляється з 2306.

`clientUpdateProhibited` блокує контакт від подальших змін — включно з тією, що зняла б цей статус,
з єдиним навмисним винятком: команда, *єдиним* вмістом якої є зняття `clientUpdateProhibited`,
приймається. Тож вихід — це окрема команда:

```python
client.contact.update("C1", rem_statuses=["clientUpdateProhibited"])
# ...і лише потім редагування
client.contact.update("C1", chg={"email": "new-contact@example.com"})
```

Поєднання розблокування і редагування в одній команді це 2304.

| Код | Значення |
|---|---|
| 1000 | застосовано |
| 2303 | такого контакту немає |
| 2304 | статус це забороняє — див. правило розблокування вище |
| 2305 | асоціація це забороняє |
| 2306 | правило реєстру відхиляє значення, або статус не з тих, що встановлює клієнт |

## delete

```python
client.contact.delete(contact_id: str) -> Response
```

```python
client.contact.delete("C1")
```

**Контакт, на який досі посилається домен, видалити неможливо** — реєстр відповідає 2305, і контакт
несе статус `linked`. Спершу відкріпіть його: спрямуйте домени на інший ідентифікатор через
[`domain.update`](domains.md#update), а потім видаляйте.

`all_contacts()` у відповіді домену — це швидкий спосіб дізнатися, які з ваших контактів ще
використовуються, бо він перелічує кожен ідентифікатор, включно з реєстрантом:

```python
in_use = set(client.domain.info("example.com.ua").all_contacts())
if "C1" not in in_use:
    client.contact.delete("C1")
```

| Код | Значення |
|---|---|
| 1000 | видалено |
| 2303 | такого контакту немає |
| 2304 | статус це забороняє (`clientDeleteProhibited`) |
| 2305 | досі пов'язаний з доменом |

## transfer

```python
client.contact.transfer(op: str,
                        contact_id: str,
                        auth_info: Optional[str] = None) -> Response
```

`op` — одне з `request`, `approve`, `reject`, `cancel`, `query`, і вирушає як атрибут `op` елемента
`<transfer>`. Тут немає ні періоду, ні комісії: трансфер контакту переносить право власності і
більше нічого.

```python
# Бік, що приймає, з кодом від поточного власника.
r = client.contact.transfer("request", "C1", "the-code")
r.code()                    # 1000, або 1001, коли рішення ухвалюється згодом
r.transfer_status()         # 'pending'

# Бік, що втрачає, після poll-сповіщення про те, що хтось попросив контакт, яким ви володієте.
client.contact.transfer("approve", "C1")
client.contact.transfer("reject", "C1")

# Бік, що приймає, відкликає власний запит.
client.contact.transfer("cancel", "C1")

# Будь-який бік: на якій це стадії?
t = client.contact.transfer("query", "C1").transfer()
t["status"], t["requested_by"], t["acting_client"], t["act_by"]
```

`transfer()` повертає все сповіщення — хто попросив, коли, хто має відповісти і до якого строку.
`act_by` — це крайній строк, після якого реєстр вирішує за вас, тож сповіщення про трансфер, що
надійшло через [poll](poll.md), — це те, на що відповідають, а не те, що підшивають.

| Код | Значення |
|---|---|
| 1000 / 1001 | прийнято; 1001 означає, що результат надійде згодом через [poll](poll.md) |
| 2201 | ви не є стороною, яка може надіслати цю операцію |
| 2202 | `auth_info` неправильний |
| 2300 | трансфер уже очікує (на повторному `request`) |
| 2301 | трансфер не очікує (на `approve`/`reject`/`cancel`/`query`) |
| 2303 | такого контакту немає |
| 2304 | статус це забороняє |
