# Poll

Усе під `client.poll`. Черга poll — це `<poll>` з **RFC 5730**, і саме так реєстр говорить із вами:
все, що стається з вашими об'єктами без вашого запиту в ту мить, надходить сюди й більше нікуди.

Вам нічого не надсилають самі й вас ніхто не викликає у відповідь. Сповіщення лежить у вашій черзі,
доки ви його не запитаєте і не підтвердите, а підтвердження знищує його в реєстрі. Обидві половини
цього речення важливі, і саме через другу більша частина цієї сторінки присвячена порядку, в якому
ви робите ці дві дії.

Кожен метод повертає [`Response`](responses.md), а код відповіді 2000 або вищий викидається як
виняток — див. [Помилки](errors.md).

## Методи

| Метод | Команда EPP |
|---|---|
| `request()` | `<poll op="req"/>` — 1301 зі сповіщенням, 1300, коли черга порожня |
| `ack(message_id)` | `<poll op="ack" msgID="…"/>` — **видаляє** сповіщення в реєстрі |
| `drain(handler, limit=0)` | двоє попередніх у циклі, з підтвердженням лише після того, як ваш зворотний виклик повернувся |

---

## request

```python
client.poll.request() -> Response
```

Просить сповіщення з голови черги. Черга є чергою: те саме сповіщення повертається на кожен
`request()`, доки його не підтверджено, тож клієнт, який опитує без підтверджень, читає одне
повідомлення вічно.

```python
notice = client.poll.request()

if notice.code() == 1300:
    return                       # нічого не чекає

notice.message_id()              # '42' — ідентифікатор, який ви передаєте в ack()
notice.message_count()           # 3 — скільки повідомлень лишається в черзі
notice.queue_message()           # текст СПОВІЩЕННЯ
notice.queue_message_lang()      # 'uk' | 'ru' | 'en'
notice.queue_date()              # '2026-08-14T10:20:00Z' — коли його поставлено в чергу
```

| Код | Значення |
|---|---|
| 1301 | сповіщення додано; `message_id()` встановлено |
| 1300 | черга порожня; `message_id()` дорівнює `None`, і підтверджувати нічого |

Обидва є 1xxx, тож `is_success()` дає `True` для кожного і жоден не викидає винятку. Розгалужуйтеся
за `message_id() is not None` — або за `code() == 1300` — а не за успіхом.

```python
notice = client.poll.request()
if notice.message_id() is not None:
    handle(notice)
    client.poll.ack(notice.message_id())
```

### Текст сповіщення — це не повідомлення результату

**`queue_message()` — це сповіщення. `message()` — ні.**

`message()` повертає `<result><msg>` — заголовок результату команди, «Command completed
successfully; ack to dequeue», однаковий у кожній poll-відповіді, яку реєстр коли-небудь надсилає.
Прочитати сповіщення через `message()` означає отримати це стале речення, викинути справжній вміст —
а підтвердження, що йде слідом, видаляє цей вміст у реєстрі. Сповіщення лежить у `<msgQ><msg>`, а це
`queue_message()`.

Та сама різниця стосується мови. `message_lang()` — це мова заголовка, яка йде за `lang`, з яким ви
увійшли; `queue_message_lang()` — це мова самого сповіщення, яку реєстр обирає з налаштувань
сповіщень вашого облікового запису. Вони не зобов'язані збігатися, тож читайте власну мову
сповіщення, а не припускайте мову сесії:

```python
text = notice.queue_message()
lang = notice.queue_message_lang() or "en"
show_to_operator(text, lang)
```

`queue_date()` — це власний рядок реєстру, як і кожна дата в цій бібліотеці: мить, коли сповіщення
поставлено в чергу, а не мить, коли ви його прочитали.

## Що несуть сповіщення

Сповіщення завжди несе текст. Деякі різновиди несуть також структуроване навантаження, і там, де
воно є, саме на нього треба реагувати: текст написано для людини, навантаження — для вашого коду.

| Різновид | Структуроване навантаження | Аксесор |
|---|---|---|
| Запит на трансфер, схвалення, відмова або скасування | `<domain:trnData>` / `<contact:trnData>` | `transfer()`, `transfer_status()` |
| Результат дії, яку реєстр завершив офлайн | `<domain:panData>` / `<contact:panData>` | `pending_action_data()` |
| Попередження про низький баланс | показники облікового запису, коли реєстр їх додає | `balance()`, `available_credit()` |
| Будь-що інше, що реєстр хоче вам сказати | немає | `queue_message()` |

### Запит на трансфер

Найвагоміше сповіщення з усіх, бо воно має крайній строк, а в мовчання є свій присуд.

```python
t = notice.transfer()
# {'status': 'pending', 'requested_by': 'ACME', 'requested_at': '2026-08-14T10:00:00Z',
#  'acting_client': 'EXAMPLE', 'act_by': '2026-08-19T10:00:00Z',
#  'expiry_date': '2028-04-01T09:15:00Z'}

if t and t["status"] == "pending" and t["acting_client"] == my_clid:
    client.domain.transfer("approve", notice.object_name())     # або "reject"
```

`act_by` — це крайній строк. **Після нього реєстр підтверджує трансфер** — він його не скасовує, —
тож реєстратор, що втрачає домен і підшиває це сповіщення замість того, щоб на нього відповісти,
втрачає домен. Вікно становить 5 днів. Див. [Домени → transfer](domains.md#transfer).

### Результат відкладеної дії

Коли команда відповідає **1001**, реєстр прийняв її і завершує офлайн. Відповідь повертається сюди:

```python
pan = notice.pending_action_data()
# {'object': 'example.com.ua', 'success': True,
#  'clTRID': 'PYTHON-SDK-20260814101500-4821-0007',
#  'svTRID': 'SRV-19700101103512-24191-00007',
#  'date': '2026-08-14T10:20:00Z'}
```

Дві речі, у яких треба бути точними:

- **Лише `success` говорить, чи спрацювало.** Оболонка `1301` означає «ось повідомлення», а не «ваша
  операція вдалася». Невдалий create надходить як цілком успішна poll-відповідь, що несе
  `success: False`.
- **`svTRID` вказує, якої саме операції це стосується.** Це svTRID *первісної* команди — тієї, який
  вам видали разом з 1001, — а не poll. Черга не обов'язково йде в тому порядку, в якому ви
  надсилали, і у вас може очікувати кілька операцій одночасно, тож зіставляйте саме за ним, а не
  припускайте, що сповіщення належить вашій останній команді.

```python
if pan is not None:
    booking = bookings_by_svtrid.get(pan["svTRID"])
    if booking is None:
        alert_operator("pending outcome for an operation we do not recognise", pan)
    elif pan["success"]:
        booking.confirm(pan["date"])
    else:
        booking.fail(notice.queue_message())
```

`pending_action_data()` повертає `None` для сповіщення, яке його не несе, а таких більшість, тож
перевіряйте це перед читанням ключів. Зіставлення відбувається за локальним іменем, тож доменне й
контактне навантаження читаються однаково, а `object` містить доменне ім'я або ідентифікатор
контакту.

### Попередження про низький баланс

Реєстр попереджає, перш ніж на рахунку скінчаться кошти, бо альтернатива — виявити це як 2104
посеред пакета. Читайте показники, а не розбирайте речення:

```python
if notice.balance() is not None:
    alert_billing(notice.available_credit())
else:
    alert_billing(client.balance().available_credit())
```

Гроші — це точний десятковий рядок, ніколи не float. Див. [Баланс](balance.md).

## ack

```python
client.poll.ack(message_id: str) -> Response
```

Підтверджує одне сповіщення, що **видаляє його в реєстрі**. Немає ні скасування видалення, ні
архіву, ні другої копії: після успішного підтвердження вміст того сповіщення існує лише там, куди
його поклав ваш код.

```python
r = client.poll.ack(notice.message_id())
r.code()             # 1000
r.message_count()    # скільки лишилося, коли реєстр це повідомив
```

Ідентифікатор, який нічого не називає — уже підтверджений або такий, що ніколи не існував, — це 2303.

| Код | Значення |
|---|---|
| 1000 | підтверджено й видалено |
| 2303 | повідомлення з таким ідентифікатором немає: уже підтверджене або ніколи не існувало |

### Підтверджуйте після обробки, ніколи до неї

Це вся операційна дисципліна черги, і її варто сформулювати як правило:

> Збережіть сповіщення або відреагуйте на нього — **і лише тоді** підтверджуйте.

Спосіб зазнати невдачі за іншого порядку тихий і невідновний. Цикл, який спершу підтверджує, а
обробляє потім, втрачає кожне сповіщення, обробка якого зірвалася, — запит на трансфер, на який
треба було відповісти за п'ять днів, результат create, що очікує і під який ви досі тримаєте
гроші, — і не лишається ні з чого повторювати спробу і ні запису про те, що щось загублено. Реєстр
його видалив, а це була єдина копія.

```python
# Хибно. Підтвердження — це фіксація роботи, якої ще не було.
notice = client.poll.request()
client.poll.ack(notice.message_id())
store(notice.queue_message())          # якщо тут виникне виняток, сповіщення вже немає

# Правильно. Ніщо не знищується, доки робота не збережена надійно.
notice = client.poll.request()
if notice.message_id() is not None:
    store(notice.queue_message())      # якщо тут виникне виняток, сповіщення досі в черзі
    client.poll.ack(notice.message_id())
```

`drain()` існує для того, щоб вам не доводилося робити це правильно вручну.

## drain

```python
client.poll.drain(handler: Callable[[Response], None], limit: int = 0) -> int
```

Читає чергу до кінця, передаючи кожне сповіщення вашому зворотному виклику і підтверджуючи його
**після** того, як виклик повернувся. Повертає кількість успішно оброблених сповіщень.

```python
processed = client.poll.drain(lambda notice: store(
    notice.message_id(),
    notice.queue_message(),
    notice.queue_message_lang(),
    notice.queue_date(),
    notice.pending_action_data(),
))
```

| Поведінка | Що це означає для вас |
|---|---|
| Підтвердження йде після повернення зворотного виклику | Сповіщення знищується лише тоді, коли ваша частина роботи виконана. |
| Зворотний виклик, що викидає виняток, зупиняє спорожнення | Виняток доходить до вас, сповіщення **не** підтверджується і лишається в голові черги. Усуньте причину і спорожнюйте знову; нічого не втрачено. |
| Спорожнення зупиняється на першому 1300 | Черга порожня. Це нормальне завершення. |
| Будь-яка інша відповідь без сповіщення викидає виняток | Відмову — закриту сесію, призупинений обліковий запис — не можна подавати як спорожнену чергу. Це викидає виняток навіть за `throw_on_failure(False)`, бо звітувати про успіх, коли нічого не прочитано, гірше за виняток. |
| `limit` обмежує кількість оброблених | `0` означає «доки не спорожніє». Черга, що наповнюється швидше, ніж ви її спорожнюєте, інакше змусила б виклик працювати нескінченно. |
| Обробник `async def` відхиляється | `ValidationException`, ще до того, як щось буде прочитано. |

Зворотний виклик, який завжди викидає виняток, бачитиме те саме сповіщення на кожному спорожненні.
Це навмисно: альтернатива — його викинути.

```python
# Спорожнюйте обмеженими пакетами, щоб один виклик не втік від вас.
while client.poll.drain(handle_notice, limit=50) == 50:
    pass
```

### Чому асинхронний обробник відхиляється

`drain()` синхронний. Функція `async def`, викликана із синхронного коду, негайно повертає
співпрограму і не виконує жодного рядка свого тіла, тож цикл підтверджував би кожне сповіщення ще до
того, як бодай одне з них було оброблене, — саме та втрата, задля запобігання якій цей метод існує,
і без жодної помилки на доказ. Загорніть співпрограму або керуйте чергою самі через `request()`
та `ack()`:

```python
import asyncio

async def handle(notice):
    await store(notice.queue_message())

# Відхиляється ще до того, як буде прочитано хоч один кадр:
#   ValidationException: poll.drain() runs synchronously and cannot await an async handler
client.poll.drain(handle)

# Загорніть її — і порядок знову належить drain.
client.poll.drain(lambda notice: asyncio.run(handle(notice)))
```

Або керуйте чергою самі, дотримуючись того самого порядку — спершу робота, потім підтвердження:

```python
async def drain_async(client):
    processed = 0
    while True:
        notice = client.poll.request()
        if notice.message_id() is None:      # 1300: черга порожня
            break
        await handle(notice)
        client.poll.ack(notice.message_id())
        processed += 1
    return processed
```

### Доставлення відбувається принаймні один раз

Якщо зривається саме підтвердження — з'єднання обривається між поверненням вашого зворотного виклику
і доставкою підтвердження, — сповіщення лишається в черзі, і наступне спорожнення знову передасть
його вам. Це безпечний напрямок відмови, і він означає, що ваш обробник має витримувати те, що
бачить сповіщення двічі.

Зробіть його ідемпотентним і використовуйте `message_id()` як ключ дедуплікації:

```python
def handle_notice(notice):
    message_id = notice.message_id()
    if already_processed(message_id):        # друге доставлення, а не друга подія
        return
    with transaction():
        store(message_id, notice.queue_message(), notice.pending_action_data())
        mark_processed(message_id)
```

Фіксуйте свою частину до підтвердження — і обидва напрямки відмови покрито: аварія до підтвердження
відтворює сповіщення, а дедуплікація його поглинає.

## Повний опитувач черги

```python
from epptools import Client, Config
from epptools.exceptions import EppException

def handle(notice):
    pan = notice.pending_action_data()
    transfer = notice.transfer()

    if pan is not None:
        reconcile_pending(pan["svTRID"], pan["success"], pan["date"])
    elif transfer is not None and transfer["status"] == "pending":
        queue_for_review(notice.object_name(), transfer["act_by"])
    elif notice.balance() is not None:
        alert_billing(notice.available_credit())
    else:
        store_operator_message(notice.queue_message(), notice.queue_message_lang())

client = Client(Config(host="epp.registry.example", clid="EXAMPLE",
                       password="your-secret", ca_file="/etc/ssl/registry-ca.pem"))
try:
    client.connect()
    client.login()
    print("handled", client.poll.drain(handle), "notices")
    client.logout()
except EppException as exc:
    print("poll run failed:", exc)
finally:
    client.disconnect()
```

Запускайте це за розкладом — зазвичай кожні кілька хвилин — і завжди спорожнюйте до 1300, а не
беріть по одному сповіщенню за запуск. Черга меншає лише тоді, коли ви підтверджуєте, а запит на
трансфер, прочитаний із запізненням на чотири дні, — це запит, на відповідь якому у вас лишився
один день.

Опитуйте в окремій сесії, якщо ваш трафік реєстрацій щільний: одна команда за раз на з'єднання —
правило, чинне скрізь у цій бібліотеці, а спорожнення, що ділить з'єднання з create, — це
спорожнення, яке має його чекати.
